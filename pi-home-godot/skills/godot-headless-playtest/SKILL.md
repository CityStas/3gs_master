# Godot headless playtest: бот, который реально играет уровень

Скриншот-харнесс (`shot.gd`: телепорт + кадр) проверяет **картинку**. Он не может
поймать баг, который проявляется только в движении: застревание в геометрии,
мёртвый прыжок, незаспавненные пули, финал, открытый раньше времени.
Для этого нужен второй харнесс - бот, который играет.

Оба живут рядом: `tools/debug/shot.gd` (GPU, кадры) и `tools/debug/playtest.gd`
(headless, геймплей). Запускать оба, а не один.

## 0. Обязательная обвязка

```bash
APPDATA="C:\\Users\\<user>\\AppData\\Roaming" \
  "E:/Programs/distr/Godot_v4.7.2-stable_win64.exe" \
  --path "<proj>" --headless res://tools/debug/playtest.tscn
```

- `APPDATA` обязателен (см. скилл `godot-headless-assets` §0), иначе в корне проекта
  появляется мусорная папка `Godot/`.
- **Вывод писать в файл, не в `| tail -N`.** Godot печатает `SCRIPT ERROR` до старта
  прогона, но `tail` буферизует всё до конца процесса: ошибка выглядит как «прогон
  висит 10 минут и молчит». С `> tools/debug/playtest.log 2>&1` ошибку видно сразу.
- Харнесс - это `Node` + отдельная сцена `playtest.tscn`, а не `--script`: нужен
  обычный цикл `_physics_process` в дереве.

## 1. Скелет `playtest.gd`

```gdscript
extends Node

const TIME_SCALE := 6.0          # ускоряем прогон; hitstop глушим
const MAX_STEPS := 9000          # ~150 игровых секунд, страховка от вечного цикла
const GOAL_X := 116.0 * 32.0
const FALL_LIMIT := 20.0 * 32.0 + 200.0
const GOD_MODE := true           # см. §6

var main: Node2D
var player: Player
var _ready_done: bool = false
var _steps: int = 0
var _max_x: float = -1e9
var _min_y: float = 1e9
var _stuck: float = 0.0
var _probe_x: float = 0.0
var _probe_timer: int = 0
var _taps: Dictionary = {}       # action -> сколько кадров ещё держать
var _backoff: int = 0
var _lunge: int = 0
var _jump_frames: int = 0

func _ready() -> void:
	Engine.time_scale = 1.0
	main = load("res://scenes/Main.tscn").instantiate()
	main.set("autostart_intro", false)   # не ждать вступление
	add_child(main)
	# add_child() вызывает Main._ready() СИНХРОННО, поэтому ссылки берём сразу,
	# без await get_tree().physics_frame.
	player = main.get("player") as Player
	...
	_ready_done = true    # ОБЯЗАТЕЛЬНО: _physics_process стартует РАНЬШЕ конца _ready,
	                      # и без флага первый кадр падает на null.
```

`_physics_process` начинается с `if not _ready_done: return`, иначе получаешь
`игрок исчез / шагов: 0` - то есть харнесс выходит на первом же кадре.

## 2. Затык мерить ОКНОМ, а не покадрово

Самая дорогая ошибка. Две неработающие версии:

| Версия | Почему не работает |
|---|---|
| `absf(velocity.x) < 12.0` | игрок держит полную скорость, упёршись в укрытие - x-скорость не падает |
| дельта позиции за кадр `< 0.5` | отдача от выстрела двигает игрока на ~1 px/кадр, «прогресс» фиксируется вечно |

Рабочая: окно 30 кадров, порог 4 px **суммарного** сдвига.

```gdscript
_probe_timer += 1
if _probe_timer >= 30:
	var progressed := absf(player.global_position.x - _probe_x) >= 4.0
	_probe_x = player.global_position.x
	_probe_timer = 0
	_stuck = 0.0 if progressed else _stuck + 30.0
```

`absf` (а не `x - _probe_x`) - сознательно: отход назад тоже считается движением,
иначе бот «залипает» в затыке после разбега.

## 3. `Input.action_press` - три ловушки

1. **`press` и `release` в одном кадре убивают tap.** Если после `_tap("jump", 10)`
   идёт безусловный `Input.action_release("jump")` (например, в блоке «держать прыжок
   на подъёме»), прыжок не происходит вообще - бот стоит вплотную к укрытию весь
   прогон. Держать только при `not _taps.has("jump")`.
2. **`_tap` не должен перезаписывать активный tap** - иначе счётчик никогда не
   дойдёт до нуля и кнопка не отпустится:
   ```gdscript
   func _tap(action: String, frames: int) -> void:
       if _taps.get(action, 0) > 0:
           return
       Input.action_press(action)
       _taps[action] = frames
   ```
3. **Имя переменной не должно совпадать с именем функции.** `var _tap: Dictionary`
   + `func _tap(...)` → `Parse Error: Function "_tap" has the same name as a
   previously declared variable`, скрипт не грузится, процесс идёт вхолостую.
   Держать словарь под именем `_taps`.

Порядок важен: харнесс - **родитель** `main` в дереве, поэтому его `_physics_process`
идёт первым, и `Input.is_action_just_pressed("jump")` в игроке видит нажатие того же
кадра. Если поменять местами - прыжок будет на кадр позже, что тоже работает, но
диагностику сбивает.

## 4. Бот обязан разворачиваться на врага

Бот, который всегда жмёт `move_right`, **не убивает никого за спиной**: он пробегает
босса, упирается в запертый финал и стреляет в стену. Плюс обязательна проверка по
вертикали - иначе он встаёт под уступом и стреляет в бетон, где враг на 96-192 px
выше, и жжёт лимит шагов до конца.

```gdscript
var foe := _nearest_enemy()
var engage := false
if foe != null:
	engage = absf(foe.global_position.x - player.global_position.x) < 200.0 \
			and absf(foe.global_position.y - player.global_position.y) < 80.0

if engage:
	if foe.global_position.x >= player.global_position.x:
		Input.action_press("move_right"); Input.action_release("move_left")
	else:
		Input.action_press("move_left");  Input.action_release("move_right")
```

Разворот делается через направление движения, а не через отдельный «aim»: `facing`
игрока следует за вводом, и стрельба сама уходит в нужную сторону.

## 5. Уступ выше прыжка с места не берётся - нужен разбег

Если уступ выше ~64 px, подойти вплотную и прыгнуть недостаточно: горизонтальная
скорость у стены нулевая, а воздушная акселерация не успевает разогнать за время
подъёма. Двухфазный цикл:

```gdscript
if _backoff > 0:
	_backoff -= 1
	Input.action_release("move_right"); Input.action_press("move_left")
	if _backoff == 0:
		_lunge = 14
elif _lunge > 0:
	_lunge -= 1
	Input.action_press("move_right"); Input.action_release("move_left")
	Input.action_press("jump")          # зажат: иначе JUMP_CUT срежет высоту
else:
	... обычный ход вправо + _tap("jump", 10) при _stuck >= 30 ...
	if _stuck >= 210.0:
		_backoff = 18
```

Порог разбега ставить **выше** порога кувырка, иначе `State.ROLL` съедает кадр, в
котором выставляется прыжок, и `_jump_buffer` остаётся нулём.

## 6. `GOD_MODE` - иначе бот не доходит

Каждое попадание ставит `State.HURT` и отбрасывает. Под огнём бот топчется на месте
и до босса не доходит, а смерть перезагружает сцену и уносит харнесс вместе с ней.
Разделять проверки:

- `GOD_MODE = true` - геометрия, триггеры, финал, убийства.
- `GOD_MODE = false` - боевка: смотреть счётчик попаданий по игроку.

```gdscript
Game.set_health(Game.max_hp)      # не даём умереть
if GOD_MODE:
	player.set("_invuln", 1.0)    # take_damage() выходит по is_invulnerable()
```

## 7. Финал ловить по флагу режиссёра, а не по координате

Игрок упирается в стену и встаёт на `3711.9` при цели `3712` - строгое
`x >= GOAL_X` не срабатывает **никогда**, прогон висит до лимита шагов.

```gdscript
if bool(main.get("_finished")) or player.global_position.x >= GOAL_X:
	_reached_goal = true
	_finish("дошёл до финиша")
```

Приватные поля читаются через `main.get("_finished")` - GDScript это позволяет.

## 8. Что печатать (иначе диагностика слепая)

Строку состояния раз в 120 шагов - обязательно с этими полями:

```
t= 8.0s x=1525 y=492 hp=5 ammo=0 hits=0 kills=5 seq=2 | cine=false state=0
  vel=122 vY=115 buf=0.00 coy=0.10 stuck=0 jmp=15 floor=false |
  Terrain<TileMapLayer>^Level | @StaticBody2D@36<StaticBody2D>^Covers
```

- `state` / `vY` / `buf` / `coy` - почему не прыгает.
- `jmp` (счётчик кадров с `velocity.y < -80`) - **доказательство, что прыжок вообще
  был**. Без него `vY=0` в срезе ничего не значит: срез попадает на кадр, когда
  игрок уже на полу. Это ловушка: `buf=0.00` при срезе раз в 120 кадров
  бесполезен (буфер живёт 0.12 игровых секунды ≈ 1.2 кадра).
- Имена и типы коллайдеров из `get_slide_collision(i)` - отличает геометрию
  (`Terrain<TileMapLayer>`) от укрытия (`StaticBody2D^Covers`) от врага.
- В финальном отчёте: `макс. x` против `GOAL_X`, `мин. y`, число сработавших сцен
  диалога, цели из `Game.objective`, «босс убит».

## 9. Баги, которые ловятся только так (реальные примеры)

Все четыре нашёл этот харнесс; скриншоты их не видели:

1. **Декоративный слой был невидимой стеной.** `TileMapLayer` берёт `TileSet`
   с физическим слоем - нужен `collision_enabled = false`.
2. **Прыжок не работал.** `_apply_gravity()` обнулял `velocity.y` по
   `is_on_floor()`, а это результат ПРОШЛОГО `move_and_slide()`: прыжок,
   выставленный выше по коду, стирался в том же кадре.
3. **Тупик в геометрии.** Пожарная лестница накрывала бетонный блок сверху -
   над головой 24 px, прыгнуть некуда. Лечится сдвигом лестницы на 3 тайла.
4. **Игрок не мог убить никого.** Сигнал `shot_fired` эмитился и никем не
   слушался - патроны тратились, пули не спавнились. Плюс обработчик попадания
   проверял `host is Enemy`, а босс - не `Enemy`: проверять
   `host.has_method("receive_hit")`, а не класс.

Плюс геймплейный пробел, который виден только по счётчику: **финал открывался при
живом боссе**. Лечится замком на триггере (`set_trigger_locked(id, bool)` в уровне,
снятие по `Game.enemy_killed("kind")` в режиссёре). Запертая зона обязана **не
выключать мониторинг** - иначе сгорит на первом входе и не сработает потом.

## 10. Чего харнесс НЕ проверяет

- Точность картинки - это `shot.gd`.
- Урон по игроку при `GOD_MODE = true` (счётчик `hits` будет нулевым).
- Смерть и рестарт: `reload_current_scene()` уносит харнесс вместе со сценой.
- Ввод с клавиатуры в фокусе окна - в headless окна нет, весь ввод синтетический.

## 11. 3D-вариант: бот по маршруту waypoint'ов

Для 3D-платформера «идти вправо» не работает: высота - часть маршрута. Уровень
отдаёт массив `route: Array[Vector3]`, бот идёт по индексу `_wp` и инкрементит его
при прибытии. Четыре грабли, каждая стоила отдельного прогона.

**1. Прибытие нельзя мерить только по XZ.** `flat.y = 0.0` - и падение в пропасть
ровно под целевой площадкой (`flat` = 2.6 м, высота −55 м) засчитывается как
«waypoint достигнут». Бот уходит на следующий пункт, вися в воздухе, а потом вечно
ходит к арене от чекпоинта. Требовать, чтобы бот не был сильно **ниже** цели:

```gdscript
if flat.length() < ARRIVE_RADIUS and _wp < level.route.size() - 1 \
        and player.global_position.y > wp.y - 4.0:
    _wp += 1
```

**2. `--start=x,y,z` + `_nearest_waypoint` выбирает последний waypoint.** Последний
пункт маршрута обычно стоит у финальных ворот: бот стартует «на финише», идёт в
столб ворот, его сносит с арены, `_keep_alive()` телепортит на чекпоинт - и цикл
повторяется. Отступать от хвоста маршрута: `_wp = mini(_wp, level.route.size() - 3)`.

**3. Отдельный детектор телепорта.** Respавн/клэмп двигает игрока на десятки метров
за один физический кадр и молча портит весь трейс (выглядит как «бот прошёл зону»).
Ловить по порогу и печатать:

```gdscript
if _last_pos != Vector3.ZERO:
    var jump := player.global_position.distance_to(_last_pos)
    if jump > 3.0:
        print("[playtest] TELEPORT %.1f m: %s -> %s | checkpoint=%s" % [
            jump, str(_last_pos), str(player.global_position), str(Game.checkpoint_point)])
_last_pos = player.global_position
```

**4. Подъём берётся только пружиной.** Если следующий waypoint выше на 2+ м, а бот
на полу - сворачивать на ближайшую пружину (группа `"springs"`), но **только пока
`is_on_floor()`**: в полёте руль обратно на пружину отменяет запуск. Пружина - не
единственный способ, поэтому проверять арифметикой: апекс прыжка (для `jump 8.0`,
`gravity 20` это 1.6 м) и «hover только снижается» - если разрыв выше апекса, без
пружины/платформы зона физически непроходима, и это баг уровня, а не бота.

## 12. Грабля VFX: автофри эффектов через `SceneTreeTimer`

Три версии, две плохие. Эффект нужно удалить через `delay`, но он может умереть
раньше (босс чистит маркеры, родитель освобождается с детьми).

| Версия | Что в логе |
|---|---|
| `create_timer(...)` + лямбда, захватившая ноду | `ERROR: Lambda capture at index 0 was freed. Passed "null" instead.` - по разу на каждый висящий эффект |
| `create_timer(...)` + `_free_later.bind(node)` | `ERROR: Error calling from signal 'timeout' to callable: 'GDScript::_free_later': Cannot convert argument 1 from Object to Object.` - `bind` на **статической** функции движок не прокидывает; смена типа параметра на `Object` не помогает |
| одноразовый `Timer`-**ребёнок** | тишина |

```gdscript
static func _autofree(node: Node, delay: float) -> void:
	if not is_instance_valid(node):
		return
	if not node.is_inside_tree():
		node.queue_free()
		return
	var timer := Timer.new()
	timer.one_shot = true
	timer.wait_time = maxf(delay, 0.01)
	timer.ignore_time_scale = true                 # hit-stop на Engine.time_scale
	timer.process_mode = Node.PROCESS_MODE_ALWAYS  # аналог process_always=true
	node.add_child(timer)
	timer.timeout.connect(node.queue_free)         # bind метода ноды, без аргументов
	timer.start()
```

Таймер, припаркованный к эффекту, умирает вместе с ним - сигнал просто не
выстреливает, и обрабатывать «ноду уже освободили» не нужно вообще.

Проверка, что грабля закрыта: `grep -c "ERROR" run.log` → остаётся только штатное
`N resources still in use at exit`. Это не утечка кода, а отчёт движка на выходе.

## 13. Скриншот-харнесс: оверлей титульника и пробуждение босса

- **`--headless` вешает `shot.tscn` намертво.** Харнесс ждёт
  `await RenderingServer.frame_post_draw` в `_process`, а без рендерера этот
  сигнал не приходит никогда: процесс печатает только баннер движка и стоит до
  SIGTERM (замер: 2m13s, повтор одиночным запуском — то же). Запускать
  **в окне**, добавив `--size=960x540`; прогон ~9 с. `playtest.tscn` этим не
  страдает — он headless-совместим, и «оба харнесса headless» — неверная
  посылка. Если скриншот-прогон «завис» — сначала проверь, не передан ли
  `--headless`, и только потом ищи баг в сцене.
- **`--call=begin` обязателен.** Без него на всех кадрах висит плашка «Press any key
  to begin» и закрывает уровень. Вызывать метод режиссёра (`main.gd: func begin()`)
  через `if _loaded.has_method(_call): _loaded.call(_call)`.
- **Босса нельзя сфотографировать от спавна.** Он спит, пока игрок не подойдёт к
  арене (`_player_near_arena()`), и до этого зарыт под полом. Нужен `--player=x,y,z`
  (телепорт игрока + камеры) **и** запас кадров на вступление: `--frames=300`.
  С `--frames=50` получишь арену без босса и без HUD-полосы.
- Формат кадров: `--shots="camX,camY,camZ|lookX,lookY,lookZ;..."` - `;` между
  кадрами, `|` между позицией камеры и точкой взгляда.

## 14. Третий харнесс: аудит уровня (объекты в пустоте и недостижимые уступы)

`playtest.gd` показывает, что уровень **проходим**. Он не показывает, что на нём
**висит в воздухе** и что на него **нельзя запрыгнуть**: бот идёт по маршруту и не
смотрит по сторонам. Для этого `tools/debug/audit.gd` + `audit.tscn`: загружает
сцену, ждёт три `physics_frame`, меряет и печатает отчёт.

```bash
APPDATA="..." "<godot>" --headless --path "<proj>" \
    res://tools/debug/audit.tscn -- "--out=res://_audit.txt"
```

**Две вещи, без которых инструмент врёт:**

1. **Луч стартует ВЫШЕ объекта**, не на `from.y + 0.05`. Верх цилиндра-коллайдера
   острова обычно на 0.2-0.3 м выше авторского Y, а пропсы укоренены в авторском Y:
   старт "чуть выше объекта" попадает внутрь тела, а `intersect_ray` не сообщает о
   выходе из него - и все 245 объектов отрапортуют "NOTHING BELOW". Рабочее:
   `from + Vector3(0, 26, 0)` вниз на 90 м.
2. **Поверхности берутся из реальной геометрии**, не из авторских чисел. Обход всех
   `StaticBody3D`, мировой AABB из каждой `CollisionShape3D`:

```gdscript
var local := cs.shape.get_debug_mesh().get_aabb()   # фолбэк: ручной разбор
for i in 8:                                          # Box/Cylinder/Sphere
    pts.append(cs.global_transform * local.get_endpoint(i))
```

Затем пары соседей: `rise = hi.top - lo.top`, `gap` по XZ, и уступ с
`rise > JUMP_APEX` без пружины в радиусе 4.5 м от нижней площадки - баг.
`JUMP_APEX` считать из констант: `jump 8.0` при `gravity 20` = **1.6 м**;
ховер **не добавляет** высоты, он только снижает - в разрыв это не зачитывать.

**Что этот харнесс ловит (реальные находки):** декор, выставленный по координатам
за кромкой острова (трава = 0.97*R, коллайдер = 0.98*R, всё дальше - висит);
"наградные" платформы с подъёмом 3.2 м при апексе 1.6 м, которые видно с маршрута
и невозможно взять; кольца-обручи и звёзды над пропастью (ложные срабатывания,
помечать как задуманные).

**Отдельная секция по врагам - обязательна.** Врагов ставят авторскими
координатами, и "стоит в воздухе над платформой" из скриншота неотличимо от
"прыгает" и от "падает в пустоту". Мерить так же, как пропсы, плюс `is_on_floor()`:

```gdscript
for n in get_tree().get_nodes_in_group("enemies"):
    var e := n as Node3D
    var g := _ground_below(space, e.global_position)
    print("%s at %s -> %+.2f m above %s  floor=%s" % [e.name, e.global_position,
        e.global_position.y - float(g["y"]), g["name"], (e as CharacterBody3D).is_on_floor()])
```

Реальные находки: три врага "челленджа" стояли в дыре между террасами
(x 117/121/119.5 при полу, кончающемся на 116.4 и начинающемся на 120.6) - двое
падали из уровня на первом кадре, третий (летающий) висел над пропастью всю игру.
Второй враг на террасе спавнился на 1.28 м выше пола и падал при старте.

**Ждать 60 физических кадров, а не 3.** Три кадра показывают высоту спавна и не
отличают "поставлен высоко" от "вообще не приземляется". Секунды хватает: пропсы
статичны, а падающий враг успевает лечь. Побочный эффект - `MovingPlatform` за
секунду успевает отъехать, это нормально.

**Обязательный сторож в самом `EnemyBase`:** враг, выставленный над пустотой, не
исчезает никогда - он падает вечно, остаётся в счётчике живых и симулируется до
конца прогона. Дешёвая страховка:
```gdscript
const KILL_Y := -60.0
# в _physics_process, до всего остального:
if global_position.y < KILL_Y:
    _fell_out()      # remove_from_group + Game.unregister_enemy + queue_free, без наград
    return
```

**Не путать с настоящим багом:** коллектибл в 1-3 м над землёй - норма (у магнита
свой радиус); кольцо-обруч в воздухе - норма (это маркер прыжка). Инструмент
печатает факты, решение принимает человек.

## 15. Грабли визуала, которые видит только глаз (а не харнесс)

- **Плоская плита, вращающаяся вокруг нормали к своей плоскости, мигает.**
  Звезда-ядро в груди босса крутилась `rotation.y`; раз в оборот вставала ребром и
  "проходила сквозь" тело. Вращать надо вокруг оси самой плиты (`rotation.z`).
  Проверять: у плоской детали толщина << радиуса - любое вращение поперёк плоскости
  даёт мерцание.
- **Снаряд, рождённый в центре модели, вылетает из неё.** `muzzle = global_position +
  Vector3(0, BODY_RADIUS, 0)` - это центр тела. Спавнить на поверхности:
  `origin + flat_dir * (RADIUS * 1.08)`.
- **Деталь, утопленная за поверхность, показывает только кончик.** Если плита
  параллельна поверхности, её надо вынести НАРУЖУ (`-RADIUS * 0.98`), иначе виден
  один луч, который читается как глюк.
- **Персонаж скользит, если `_update_visual` делает только доворот + squash.**
  Гейт (шаг) = подпрыгивание `|sin|*k*walk` + попеременный подъём ног от скорости.
  Визуальный хоп вешать на `_model`, а не на корень: коллайдер-капсула стоит на
  корне, и смещение корня рассинхронизирует попадания.
- **Декор, повторяющий меш и цвет коллектибла, читается как сломанный пикап.**
  Постамент со звездой r=1.7 тем же золотом и с теми же искрами игрок пытается
  подобрать. Либо делать настоящим `_star(pos, value, big)`, либо менять цвет и меш.
- **Экран-заставка:** игровой HUD (сердца, счётчик, бейдж способности, тост) и
  баннер зоны надо **гасить**, пока заставка видна. Триггер зоны срабатывает в
  `_ready()`, т.е. под заставкой, и баннер всплывает прямо сквозь заголовок -
  откладывать его в очередь и проигрывать в момент старта.
- **Заголовок на дефолтном шрифте читается как заглушка.** Godot-овский UI-шрифт
  для `PASTEL PEAKS` - это "ещё не сделали". Брать rounded/bubble-шрифт (SIL OFL)
  из репы google/fonts, класть в `assets/fonts/`, грузить через
  `ResourceLoader.exists()` + `load()` и навешивать только на заставку:
  `add_theme_font_override("font", f)` + `outline_size` +
  `font_outline_color = white` даёт "стикер". Остальной UI не трогать. Не забыть
  `--headless --editor --quit` один раз - без импорта `load()` вернёт null.
  **Что реально читается как bubble:** `ofl/titanone/TitanOne-Regular.ttf` -
  толстый, круглый, пружинистый, ровно то, что просят под "милый пузырьковый".
  **`ofl/bubblegumsans` НЕ подходит**, несмотря на название: по начертанию это
  обычный rounded-гротеск, заказчик такой шрифт браком и назвал. Альтернативы,
  если нужен не такой жирный: `ofl/fredoka/Fredoka[wdth,wght].ttf` (вариативный,
  `FontVariation.variation_opentype = {"wght": 700}`), `ofl/baloo2/Baloo2[wght].ttf`.
  Проверять глазами по скриншоту заставки, а не по названию семейства.
- **`Label` внутри `Panel` не центруется одним `horizontal_alignment`.** Лейбл -
  не контейнерный ребёнок, он держит минимальный размер и садится в левый верх
  панели: цифры "1 2 3" в цветных кружках заставки выглядели съехавшими.
  Сначала растянуть (`set_anchors_preset(PRESET_FULL_RECT)`), потом выравнивать:
  ```gdscript
  var num := _label(index, 18, Palette.INK)
  _anchor_full(num)                                  # иначе центрировать нечего
  num.horizontal_alignment = HORIZONTAL_ALIGNMENT_CENTER
  num.vertical_alignment = VERTICAL_ALIGNMENT_CENTER
  pip.add_child(num)
  ```
- **AoE-волна от тела бьёт не туда, куда смотришь.** Ударная волна босса - круг
  вокруг *босса*, а не вокруг арены. Босс, прижатый к краю (`_keep_in_arena`),
  отправляет её на `arena_radius + reach` от центра - у нас это 28 м при
  платформе 15 м, и игрок на подходном острове получал урон от волны, до него не
  дошедшей. Хит-тест надо клипать по диску пола (`bounds_center` / `bounds_radius`),
  визуал оставлять как есть. Правило общее: **любой радиус урона, привязанный к
  подвижному телу, обязан иметь границу арены**, иначе он уезжает вместе с телом.
- **Маркер маршрута, выставленный по Y "на глаз", тонет в следующей платформе.**
  Кольцо-обруч - это `ring(...)` + `rotation.x = PI/2`, то есть вертикальное
  кольцо, занимающее `pos.y +/- outer_radius`. Кольца на y = 11.0 и 17.5 оказались
  ВНУТРИ цилиндров террас с верхом 14.30 и 19.30 - наружу торчал один сегмент,
  читалось как глюк текстуры. Считать надо не "между террасами красиво", а
  `pos.y - outer_radius > surface_top` целевой платформы И либо `y > top`, либо
  горизонтальная дистанция > радиуса коллайдера - для каждой платформы, включая
  нижнюю. Ставить их на реальную дугу пружины, а не по прямой между центрами.
- **Механика с одноразовым ресурсом тихо умирает, и это не видно в pass/fail.**
  Q стрелял "звездой" только при запасённом враге; врагов без способности на
  уровне шесть, поэтому кнопка срабатывала один раз и дальше читалась как
  сломанная. Симптом в отчёте бота - `attack presses: 155`, но ноль фактов
  выстрела. Лечится не догадками, а счётчиком сигнала в харнессе
  (`player.star_spat.connect(...)` -> `stars launched (Q): 15`) плюс явным
  фолбэком: кнопка стрельбы обязана что-то делать всегда, пусть слабее и с
  большим кулдауном. **Правило: у каждой кнопки управления должен быть
  безусловный ответ, а у одноразового ресурса - путь восстановления.**

- **Награда, лежащая РЯДОМ с движущимся пропом, читается как бесхозная геометрия.**
  Единственная движущаяся платформа уровня выглядела ненужной, а её звезда -
  приклеенной ни к чему: звезда стояла в **мировых** координатах в 2.25 м над декой
  и не ехала с плитой. Лечение - не подгонять координаты, а **сделать пикап ребёнком
  пропа** (локальные `(0, height, 0)`), тогда он едет вместе с ним:
  ```gdscript
  func _star_on(parent: Node3D, height: float, value: int = 1) -> void:
  	var s := StarCollectible.new()
  	s.value = value
  	s.position = Vector3(0, height, 0)   # до add_child: _ready() защёлкивает _base_y
  	parent.add_child(s)
  	star_total += value
  ```
  Магнит пикапа (`global_position += ...`) и боб (`global_position.y = ...`) с
  движущимся родителем работают: родитель ходит по XZ, а пикап трогает только Y.
  Проверка - два скриншота с одной камеры на разных кадрах: пикап обязан сместиться
  на столько же, на сколько уехал проп. Плюс `--start` прямо на деку: счётчик
  звёзд должен прибавиться в **первом же кадре**.
- **Плоскую деталь, которую надо поставить "на ребро", нельзя крутить тем же
  свойством, что и её спин.** `ProcMesh.ring` - плоский аннулус в XZ (нормаль +Y).
  Чтобы обруч врат встал вертикально и смотрел в проход, нужно
  `_ring.rotation.x = PI * 0.5`. Но у Эйлера Godot порядок **YXZ**: `rotation.y`
  применяется последним, то есть вокруг **вертикальной** оси родителя - и спин тем
  же `rotation.y` даёт "вращающуюся дверь", которая дважды за оборот встаёт ребром
  и визуально исчезает. Спин выносится в дочерний узел: у поднятого обруча
  локальный `Y` узла-держателя **и есть** его нормаль, поэтому `_spin.rotation.y`
  крутит кольцо в своей плоскости (Stargate).
- **Раму-портал надо разворачивать по направлению подхода, а не по мировым осям.**
  Врата строились как "стойки в локальных `+/-X`, арка по X" - проём смотрит в
  `+/-Z`, а игрок приходит по `+X` и проходит **мимо** стоек. Симптом у заказчика:
  "просто кольцо среди платформы, не понятно зачем". Лечится одним
  `gate.rotation.y = PI * 0.5`. Проверять камерой строго вдоль маршрута: стойки
  должны оказаться слева и справа, а не спереди и сзади.

## 16. `AnimatableBody3D` + `sync_to_physics`: запись transform молча теряется

Симптом: движущаяся платформа **стоит в мировом нуле** и ездит там, хотя в билдере
ей назначен `global_position`. Выглядит как "голубая пластина ездит по стартовому
острову и ничего не делает".

Причина: `sync_to_physics = true` (включается в `_ready()`) отдаёт transform тела
физическому серверу. После `add_child()` запись `position` / `global_position` /
`global_transform` **игнорируется без единой ошибки в логе** - значение читается
обратно нулевым. Классический порядок билдера (new -> задать свойства ->
`add_child` -> задать позицию) ломается ровно на последнем шаге.

Матрица проверки (одна проба, 5 вариантов, снимает вопрос за один прогон):

| как назначаем | результат |
|---|---|
| `position` ПОСЛЕ `add_child` | потеряно -> (0,0,0) |
| `global_transform` ПОСЛЕ `add_child` | потеряно -> (0,0,0) |
| `position` ДО `add_child` | **работает** |
| `sync_to_physics = false`, затем `position` | работает (но теряется перенос скорости) |
| `set_deferred("position", ...)` | работает (следующий idle-кадр) |

Лечение - **позиция до `add_child`**, `sync_to_physics` оставить включённым:
он нужен, чтобы стоящий на платформе `CharacterBody3D` унаследовал её скорость.

Второй слой той же грабли: если платформа защёлкивает свою опорную точку в
`_ready()` (`_origin = position`), она запомнит **ещё не выставленный** transform и
на первом же `_physics_process` уедет в ноль, даже когда позиция назначена верно.
Защёлкивать лениво, на первом физическом кадре:

```gdscript
func _physics_process(delta: float) -> void:
	if not _origin_ready:
		_origin = position
		_origin_ready = true
```

**Как искать такие вещи:** аудит уровня печатает верхние Y всех `StaticBody3D`
(а `AnimatableBody3D` - его наследник), поэтому "платформа не там" видно как
строку с чужими координатами. Дальше - временный `probe.tscn` на 20 строк
(загрузить сцену, распечатать `position` до/после `add_child` и на 3 кадрах),
и удалить его после ответа. Дешевле, чем гадать по коду.

## 17. Плейтест-флак: бот без способности физически не может добить босса

Симптом: один и тот же уровень проходит с первого прогона и валится по
`step limit reached` со второго. В отчёте - `ability at end:` пусто,
`attack presses: 0`, `hits taken: 76`, босс `40/40` (он **регенерирует**, поэтому
без способности неубиваем). Игра при этом исправна: точечный прогон
`--start=<у арены> --ability=sword` проходит с первого раза.

**Не искать причину в игре - сначала проверить порядок блоков в `_steer()`.**
У нас погоня за носителем способности стояла **после** обхода пружин и
безусловно перезаписывала `dir`. Когда единственный оставшийся носитель - враг на
**следующей** террасе, бот шёл прямо на него, сходил с края террасы, терял
`is_on_floor()` (а вместе с ним и весь блок пружин) и в hover уезжал в пустоту.
Оба фикса:

1. **Порядок:** погоня за носителем - ДО обхода пружин, иначе пружина не может
   выиграть, когда следующая точка маршрута выше.
2. **Вертикальный фильтр в выборе цели:** носитель на другой высоте - не цель.
   ```gdscript
   func _nearest_carrier(range: float, max_dy: float = 2.5) -> Node3D:
   	...
   	if absf(e.global_position.y - player.global_position.y) > max_dy:
   		continue
   ```
   Одновысотные наземные враги дают `|dy| ~ 0.3`, так что порог ничего живого
   не отсекает. Тот же фильтр обязателен и в блоке вдоха: тянуть в конус врага
   в 5 м над головой бессмысленно.

**Правило:** любой "магнит к цели" в боте (носитель способности, пикап, босс)
обязан иметь фильтр по высоте. Цель, к которой нельзя дойти пешком, превращает
навигацию в поход в пустоту.

**И обязательно проверять фикс двумя прогонами подряд**, а не одним: у бота есть
RNG (таймеры прыжков врагов), и один зелёный прогон ничего не доказывает.
После фикса: 74.5 с и 76.2 с, оба `level finished: true`, `hits taken: 1`.

## 18. Чеклист приёмки GDD прогонять построчно - и по коду, и харнессом

Когда в GDD есть раздел вида "Playtest checklist / acceptance criteria", его надо
пройти **пункт за пунктом**, а не «в целом всё работает». Из десяти пунктов
обычно 1-2 тихо не реализованы, и харнесс их не ловит, потому что игра
*играбельна*.

Реальный пример: «Inhale selects valid enemies and respects line of sight».
Вдох был сделан через `Area3D.get_overlapping_bodies()` + конус + дистанцию -
и это **не** line of sight: сфера не различает врага за кромкой террасы и врага
в чистом поле. Бот доходил до финала, скриншоты были красивые, пункт - не выполнен.

```gdscript
# LOS поверх Area3D+конуса. Два луча (грудь и голова), достаточно любого
# чистого - низкий камень перед врагом не должен отменять захват.
func _has_sight(from: Vector3, e: Node3D) -> bool:
	var space := get_world_3d().direct_space_state
	return _ray_clear(space, from, e.global_position + Vector3(0, 0.35, 0)) \
		or _ray_clear(space, from, e.global_position + Vector3(0, 1.15, 0))

func _ray_clear(space: PhysicsDirectSpaceState3D, from: Vector3, to: Vector3) -> bool:
	var q := PhysicsRayQueryParameters3D.create(from, to, Combat.MASK_WORLD)
	return space.intersect_ray(q).is_empty()
```

`MASK_WORLD` (`1 << 0`) обязателен: враги и игрок сидят на своих слоях, поэтому
цель не может заблокировать собственный луч, а `hit_from_inside` не срабатывает
от капсулы игрока.

**Как проверять пункты, которые кодом не проверяются:** постоянные времени брать
из кода (`TELEGRAPH = 0.55`, `_set_state(POUND_RAISE, 0.9)`) и сравнивать с
человеческой реакцией (~0.25 с); «хитбокс синхронен с визуалом» проверять
архитектурно - один узел владеет и мешем, и хит-тестом, а не два, которые могут
разъехаться; «экран победы» - снимать скриншотом через форс-флаг
(`--finish=1`), а не ждать реального прохождения.

**И сразу проверять, не сломал ли фикс бота:** после добавления LOS два прогона
подряд остались зелёными (`hits taken: 1`), то есть вдох не перестал работать.

**Побочный эффект, который тоже надо чинить:** любой новый `StaticBody3D`
(в нашем случае кольцо стен-панелей вокруг арены) попадает в список «standable
surfaces» аудита и печатает фальшивые `RISE ... gap 0.0` шаги на себя. Фильтровать
по группе: `if b.is_in_group("arena_barrier"): continue`.

## 19. HUD целиком в коде: титульник, пауза, переименование игры

Когда весь UI собирается кодом (`Hud extends CanvasLayer` + `_build_*()`), правки
заставки и экрана паузы - это правки одного файла, и проверяются они тем же
shot-харнессом, что и мир. Грабли, которые стоили итераций:

**Логотип-PNG вместо текстового заголовка.** `TextureRect` с якорями CENTER и
`pivot_offset` в середину **до** пульсации:

```gdscript
var logo_h := LOGO_WIDTH * LOGO_ASPECT          # 793.0/1983.0, из размера файла
plate.set_anchors_preset(Control.PRESET_CENTER)
plate.size = Vector2(LOGO_WIDTH, logo_h)
plate.position = Vector2(-LOGO_WIDTH * 0.5, -logo_h * 0.5)
plate.pivot_offset = Vector2(LOGO_WIDTH, logo_h) * 0.5   # без этого уезжает вбок
plate.expand_mode = TextureRect.EXPAND_IGNORE_SIZE
plate.stretch_mode = TextureRect.STRETCH_KEEP_ASPECT_CENTERED
```

`scale` у `Control` растёт от левого верхнего угла. Если пивот не переставить,
пульсация выглядит как дрожание со сдвигом вправо, а не как дыхание.

Амплитуду держать в районе 3-4 %: на логотипе шириной 880 px больше читается уже
как зум, а не как сердцебиение. Пульсацию писать в `_process` через
`sin(_ui_time * k)`, а не твином, - твин для этого надо перезапускать.

**`modulate` родителя, а не ребёнка.** Если у ребёнка `modulate` переписывается
каждый кадр (дышащая подпись «PRESS ANY KEY»), твин на нём умирает на первом же
кадре. Твинить надо корень карточки: `modulate` умножается вниз по дереву, поэтому
один твин накрывает и фон, и логотип, и подпись.

**Панель по размеру контента центровать `CenterContainer`.** Ручной
`box.position = Vector2(-W*0.5, -H*0.5)` работает ровно до первой правки текста:
панель паузы выросла с двух строк подсказок до четырёх блоков, и офсет, подобранный
на глаз, промахнулся на 65 px. Правильно:

```gdscript
var centre := CenterContainer.new()
_anchor_full(centre)
_pause_root.add_child(centre)
var box := _panel(Color(1, 1, 1, 0.93), 22.0)
box.custom_minimum_size = Vector2(PAUSE_PANEL_W, 0)   # ширина - жёстко, высота - по контенту
centre.add_child(box)
```

**Сетка вместо `HFlowContainer` для «ровно».** Flow набил 5 чипов в первую строку и
3 во вторую - читается как случайность. `GridContainer` с `columns = 4` и
`size_flags_horizontal = Control.SIZE_SHRINK_CENTER` даёт две ровные строки по 4, и
колонки выравниваются по самому широкому элементу:

```gdscript
var grid := GridContainer.new()
grid.columns = 4
grid.add_theme_constant_override("h_separation", 22)
grid.add_theme_constant_override("v_separation", 10)
grid.size_flags_horizontal = Control.SIZE_SHRINK_CENTER
```

**Пульсацию проверять ДВУМЯ кадрами на разных фазах, а не одним.** Один скриншот
не отличает «пульсирует» от «стоит на месте». `_ui_time ≈ frames/60`, поэтому
экстремумы считать заранее: для `scale = 1 + 0.035*sin(2.2*t)` максимум на
`t = π/(2*2.2) = 0.714 с` → `--frames=43`, минимум на `t = 3π/(2*2.2) = 2.14 с` →
`--frames=128`. Совпадение картинок = пульсации нет.

**Проверять фазу дыхания у текста тоже.** Подпись с альфой `0.55 + 0.45*sin(2.6*t)`
на неудачном кадре выглядит бледной и читается как «сломанная вёрстка», хотя это
нормальный минимум пульса. Для показа пользователю брать кадр около максимума
(`--frames=36`).

**Пауза до старта - отдельный баг, который вылезает при переделке титульника.**
`Hud.set_paused(true)` прячет интро-рут, а `show_intro(true)` вызывается только из
`_build_hud()`. Значит одно нажатие Esc на заставке съедало титульную карточку до
конца сессии и выбрасывало игрока в запущенный прогон без карточки. Лечится
гардом в `Main.toggle_pause()`: `if Game.finished or not _started: return`.

**Переименование игры.** Искать `grep -rniE "старое[ _-]*название"` по всему
проекту, но **не трогать** дампы исходного GDD (`_gdd.txt`, сам PDF) - это источник,
а не игра. Менять: `project.godot: config/name`, докстринги классов, фолбэк-текст
заголовка. Прилагательное в описании арт-стиля («pastel palette», имена шейдеров
`pastel_toon.gdshader`) к названию не относится и переименованию не подлежит.

**Сложность босса: HP - единственный рычаг, если броня упирается в 1.**
`take_damage` вида `maxi(1, round(amount * ARMOR_MULT))` означает, что вне окна
уязвимости любой удар всё равно снимает минимум 1 HP. Значит броня не сокращает
число ударов, и «бой тянется» лечится только пулом. `40 / 1.3 = 30.8` → `MAX_HP = 31`.
Пороги фаз, если они записаны как `hp / MAX_HP`, масштабируются сами - проверять
не надо, но прогон сделать: `attack presses` упало 177 → 149 при том же результате.

## 20. Флаг `--mute` и толчок, который стирается `move_toward`

### Тестовые прогоны запускать без звука

Пользователь просит глушить игру на тестах. Ставить это по одному месту в каждом
харнессе не надо - точка входа одна, автозагрузка аудио:

```gdscript
func _ready() -> void:
	process_mode = Node.PROCESS_MODE_ALWAYS
	_apply_mute_flag()
	...

## Читать ОБА списка: у харнессов флаги идут после `--` и попадают в
## `get_cmdline_user_args()`, а `godot --mute` - в `get_cmdline_args()`.
func _apply_mute_flag() -> void:
	for source in [OS.get_cmdline_args(), OS.get_cmdline_user_args()]:
		for a in source:
			if a.lstrip("-").split("=", true, 1)[0].to_lower() == "mute":
				AudioServer.set_bus_mute(AudioServer.get_bus_index("Master"), true)
				print("[Sfx] muted (--mute)")
				return
```

`print` оставить: лог становится самодокументируемым, видно, что прогон был тихим.
Если в проекте есть подшины, глушить `Master` достаточно только когда всё сведено
в него (проверить `BUS_SFX` / `BUS_MUSIC`), иначе перечислять шины.

### Импульс в `velocity` не работает - толчок обязан жить в `target`

Классика при добавлении ускорителей/пружин/отдачи. Наивная версия:

```gdscript
	p.velocity.x += dir.x * KICK      # НЕ РАБОТАЕТ
```

Бесполезна, если горизонтальное движение считается так:

```gdscript
	var target := wish * speed
	velocity.x = move_toward(velocity.x, target.x, rate * delta)
```

`move_toward` на следующем же кадре тянет скорость обратно к `target` и съедает
импульс за ~0.15 с. Толчок надо добавлять **к цели** и гасить его по таймеру:

```gdscript
	if _boost_time > 0.0:
		target += _boost_dir * _boost_push * (_boost_time / _boost_duration)
		if target.length() > MAX_WALK_SPEED:
			target = target.normalized() * MAX_WALK_SPEED
```

Два вывода из этого:
- **толчок, а не множитель.** Множитель (`speed *= 1.5`) ничего не даёт игроку,
  который летит без ввода - например, на дуге пружины. Толчок даёт.
- **потолок обязателен.** Цепочка из нескольких ускорителей складывается; без
  `MAX_WALK_SPEED` игрок разгоняется до скорости, под которую уровень не строился.

Повторное срабатывание во время действия брать по максимуму, а не складывать:

```gdscript
	if push <= _boost_push * (_boost_time / maxf(_boost_duration, 0.001)):
		return
```

### Как измерять эффект, а не спорить о нём

Скриншот тут не докажет ничего (кадр не показывает, быстрее ли игрок). Дешёвый
способ - временный принт в момент срабатывания плюс отложенный замер:

```gdscript
	print("[ring] TEMP vel=", p.velocity.length())
	get_tree().create_timer(0.3).timeout.connect(func() -> void:
		print("[ring] TEMP vel after 0.3s = ", p.velocity.length()))
```

Даёт пару чисел вида «вход 6.18 -> через 0.3 с 8.5». **Принт потом убрать и
проверить `grep TEMP` по файлу** - иначе отладочный вывод уедет в коммит.

### Декор, который выглядит механикой, - это баг

Кольцо-указатель без триггера читается игроком как ворота, и первое, что он
сообщает: «они будто разгоняют». Форма обещает функцию. Либо функция есть, либо
объект должен выглядеть как указатель (флажок, стрелка, полоса), а не как то,
сквозь что проходят.

### Ориентация кольца: два поворота, а не один

`ProcMesh.ring` - плоский аннулус в XZ, нормаль +Y. Чтобы получить ворота, сквозь
которые бегут вдоль X, нужны **оба** поворота:

```gdscript
	rotation = Vector3(PI * 0.5, PI * 0.5, 0.0)   # YXZ: Y применяется последним
```

С одним `rotation.x` плоскость XY, нормаль по Z - кольцо стоит ребром к бегуну и
читается как яркая полоска. Симптом в отчёте: «кольца-полоски повёрнутые».

Триггер делать **по размеру отверстия**: `CylinderShape3D(radius = INNER)`, ось -
локальный Y узла, который после поворота и есть нормаль кольца. Тогда объём
совпадает с дыркой и обод не засчитывается.

И **материал дублировать**, если кольцо должно мигать: `Palette.mat` кэширует по
(цвет, опции), поэтому `set_shader_parameter` на общем инстансе зажжёт все кольца
того же цвета разом. `var m: ShaderMaterial = shared.duplicate()`.

## 21. Пружина у кромки стреляет игрока в соффит следующей террасы

Симптом от игрока: «застрял на прыжке вверх от платформы прыжка - уровень слишком
близко, врезаешься при прыжке и падаешь вниз». Это не «бот тупой» и не «прыжок
слабый». Это геометрия.

**Механика провала.** Пружина задаёт `launch_power` как **скорость**, поэтому
высота дуги `h(t) = v*t - g*t²/2` набирается постепенно: апекс только к
`t = v/g` (при `v=19`, `g=20` это **0.95 с**). Если до габарита следующей террасы
меньше ~2 м, игрок проходит их за 0.2-0.3 с - то есть ещё на подъёме - и бьётся
в **нижнюю** плоскость её коллайдера.

Особенно коварно, когда коллайдеры соседних островов **перекрываются по X**: у
террас вида `_island((88,7,0), 6.5)` и `_island((99,14,-2), 6.0)` коллайдеры
(радиус `R*0.98`) дают 81.63..94.37 и 93.12..104.88 - перекрытие 1.25 м. Пружина,
стоящая визуально «на своей террасе», фактически уже под свесом следующей.

**Проверка перед тем, как двигать что-либо.** Посчитать два числа:

```
t_edge   = (edge_x - spring_x) / walk_speed
rise     = v*t_edge - 0.5*g*t_edge²
clear    = rise - (target_top - spring_y)
```

`clear > 0` - дуга выходит выше целевой поверхности **до** входа в её габарит.
В разобранном случае: было `spring_x = 92.0`, `edge_x = 93.12`, `walk = 6` →
`t = 0.19`, `rise = 3.3` при нужных 7.3 - провал 4 м. Стало `spring_x = 89.5`
→ `t = 0.60`, `rise = 7.8` - запас 0.5 м, посадка на `x ≈ 97.7` при центре
террасы 99.

**Правило.** Ставить пружину так, чтобы к моменту входа в габарит цели дуга уже
превышала верх её поверхности, и целиться в **центр** целевого диска, а не в
ближнюю кромку. Если места мало - поднимать `launch_power`, а не двигать пружину
к краю: прижатая к кромке пружина читается как ловушка.

**Как убедиться, что починено.** По телеметрии харнесса, а не по скриншоту. В
отчёте ищите строку состояния в момент посадки - у бота должно быть
`st=RUN floor=true` на нужной высоте, `stuck=0`, и счётчик `jmp` должен расти
**монотонно**, без возврата. Сигнатура старого бага - падение `st=FALL` с
`vY ≈ -24.0` сразу после прыжка и счётчик `jmp`, застывший на месте.

Сравнивать прогоны **таблицей** (`steps`, `hits taken`, `st=FALL`), а не «стало
лучше»: после такой правки исчезает конкретная строка падения, и это видно
только в диффе логов. Заодно проверяется, что прогон не стал длиннее - снятие
бонка обычно **ускоряет** бота (в разобранном случае 69-70 с → 57.8 с).

## 22. Гейт, который плейтест не проверит: двусторонний пробник

Есть класс правок, который бот-плейтест **физически не может** подтвердить. Пример:
урон по боссу разрешён только изнутри арены. Бот выигрывает бой, ни разу в нём не
умерев, - то есть никогда не окажется снаружи круга в момент живого боя. Прогон
зелёный и до, и после правки. Такую правку надо проверять отдельным харнессом.

**Правило: пробник обязан быть двусторонним.** Проверка «снаружи урона нет»
проходит и на гейте, который блокирует **вообще всё** - а это уже сломанный бой.
Поэтому сначала удар изнутри с требованием, чтобы он **прошёл**, и только потом
удар снаружи с требованием, чтобы не прошёл. Два `PASS` в логе, не один.

Скелет (отдельный `tools/debug/<name>_probe.tscn`, грузит `main.tscn`, зовёт
`begin()`, гоняет фазы по `_physics_process`):

```gdscript
const HIT := 5
var _phase := 0
var _wait := 0
var _before := 0.0

# фаза 0: встать внутрь, ждать выхода босса из INTRO (иначе take_damage
#          отсечёт по state, и тест докажет не гейт, а state)
# фаза 1: запомнить hp, take_damage(5, player.global_position)
# фаза 2: hp упал -> inside_result=PASS
# фаза 3: встать наружу, дать барьеру пересчитаться, take_damage(...)
# фаза 4: hp не изменился -> outside_result=PASS, quit()
```

Три обязательные детали, без которых тест врёт:

- **Позицию игрока писать каждый кадр** (`global_position = pos; velocity = ZERO`) -
  иначе CharacterBody3D упадёт и уедет, и «снаружи» окажется не там, где задумано.
- **Печатать состояние босса рядом с результатом** (`state`, `engaged`). Если
  `take_damage` отсечёт удар по `state == INTRO`, `outside_result=PASS` будет
  ложным: гейт ни при чём. В разобранном случае `state=1` (IDLE) и
  `engaged=true` - вот это и делает вывод доказательным.
- **Держать радиус в одном месте.** Гейт не должен дублировать число из
  геометрии: пусть владелец геометрии отдаёт свой тест публичным методом
  (`ArenaBarrier.player_inside()`), а второй участник его **спрашивает**. Два
  независимых радиуса разъедутся на первой же правке.

Такой пробник дешевле оставить в репозитории как регрессионный, чем писать заново:
он ловит возврат дыры при любой будущей правке арены.

## 23. Бот сходит с кромки в разрыв: состояние, которое запрещает прыжок

Симптом: бот **каждый** прогон падает в одну и ту же пропасть, `min y reached`
уходит на плоскость смерти, в логе `st=FALL` с `vY ≈ -24.0` сразу после кромки.
Выглядит как «бот не умеет прыгать через разрыв», хотя тест разрыва у него есть
и срабатывает.

**Не спешить винить навигацию - сначала проверить, не запрещён ли прыжок
текущим состоянием игрока.** В разобранном случае виновата одна строка в
`player.gd`:

```gdscript
if jump_buffer > 0.0 and can_jump and state != State.HURT and state != State.INHALE:
```

Прыжок **отказывает** в `INHALE`, и вдобавок `INHALE_SPEED_MULT := 0.45` режет
ходьбу вдвое. Безобидный учебный враг, стоящий за 4.5 м до кромки внутри радиуса
вдоха, превращает подход к разрыву в медленный сход с обрыва без высоты - а
ховер только опускает, так что разрыв уже не берётся.

Проверять по логу: `st=INHALE` вместе с `vel` примерно вдвое ниже обычной
скорости ходьбы - это подпись. Плюс сам `jmp` не растёт, хотя `far = -999`
(тест разрыва отработал).

**Граница «баг уровня / баг бота».** Если состояние снимается отпусканием
кнопки - это не ловушка для игрока (он отпустит и прыгнет), и чинить надо
харнесс, а не уровень. Ловушкой это стало бы только при toggle-вводе или если
враг наносит урон.

### Порядок вызовов в кадре решает, кто кого перебьёт

Первая попытка - `Input.action_release("inhale")` прямо в прыжковом решении -
**не дала ничего**: логи до и после совпали побайтово. Причина в порядке строк
`_physics_process`:

```gdscript
	_steer(delta)     # здесь решается прыжок  -> release
	_combat()         # здесь жмётся вдох      -> press перебивает
```

Отпускание и нажатие в одном кадре, побеждает последнее. Лечится **флагом между
ними**, а не перестановкой: `_steer` ставит `_gap_ahead = true`, `_combat`
читает и не жмёт.

Две детали, без которых флаг не работает:

- **сбрасывать флаг каждый кадр** в начале того же блока, иначе он залипнет и
  бот перестанет вдыхать вообще;
- **отпускать явно**, а не просто «не жать»: действия в Godot level-triggered,
  нажатие с прошлого кадра само не снимется. Значит
  `if можно and not _gap_ahead: press else: release`.

Мораль общая: прежде чем менять логику бота, посмотреть, **в каком порядке**
вызываются его же функции в кадре. Диагноз «условие неверное» и диагноз «условие
верное, но его перебивают» требуют разных правок, а выглядят одинаково.

### Замер эффекта

Сравнивать не «стало лучше», а числа: `steps`/время, `min y reached`, счётчик
кадров ховера, `st=FALL`. В разобранном случае: 3473 шага / 57.9 с ->
2658 / 44.3 с, `min y` `-30.0` -> `0.1`, `hov` 373 -> 111, `hits taken` 2 -> 1.
`min y` - самый честный индикатор: пока он равен плоскости смерти, бот где-то
падает, даже если прогон «зелёный».

## 24. `ERROR: N resources still in use at exit` — как отличить гонку от регресса

После прогона может появиться хвост, которого вчера не было:

```
WARNING: 8 ObjectDB instances were leaked at exit (run with `--verbose` for details).
ERROR: 8 resources still in use at exit (run with `--verbose for details`).
```

Прежде чем объявлять регресс — определить, детерминирован он или нет.

### 24.1 Сначала узнать, ЧТО течёт

Без `--verbose` в логе только счётчик. С `--verbose` в конце файла появляются
имена:

```
Leaked instance: AudioStreamPlaybackOggVorbis:... - Reference count: 1
Resource still in use: res://assets/audio/music/theme.ogg (AudioStreamOggVorbis)
Resource still in use: res://assets/audio/sfx/step.ogg (AudioStreamOggVorbis)
```

```bash
godot --headless --verbose --path . res://tools/debug/playtest.tscn -- --mute > _v.log 2>&1
grep -nE "Leaked instance|Resource still in use" _v.log | head -20
```

### 24.2 Затем проверить детерминированность

Гонять **одну и ту же** команду с разным числом шагов и смотреть, как ведёт себя
счётчик. Признак гонки — немонотонность:

| `--steps` | лик |
|---|---|
| 20 | нет |
| 50 | **есть** |
| 200 | нет |
| 400 | **есть** |
| 400 | **есть** |

Длина прогона не коррелирует с ликом -> это **гонка на выключении**, а не
накопление. На Bubble Peaks так выяснилось, что течёт аудио-плейбек: если в
момент `quit()` ещё жив `AudioStreamPlaybackOggVorbis`, движок рапортует лик.
Число инстансов растёт с числом проигранных звуков (`hits taken` 1 -> 8,
`hits taken` 3 -> 18).

### 24.3 Обязательный A/B на «а не я ли это сломал»

Если между чистым и грязным прогоном правился `project.godot` — проверить именно
свою правку, а не гадать. Пример: подозрение на `config/icon` (крупный PNG,
который держит `DisplayServer`):

```bash
cp project.godot _project.godot.bak
# ветка A: текущее значение; прогнать, записать счётчик
sed -i 's|^config/icon=.*|config/icon="res://icon.svg"|' project.godot
# ветка B: прогнать, записать счётчик
cp _project.godot.bak project.godot
grep -n "^config/icon" project.godot   # ОБЯЗАТЕЛЬНО убедиться в откате
```

Если обе ветки текут одинаково — правка ни при чём, причина была раньше.

### 24.4 Что считать «зелёным» прогоном

Лик на выключении **не влияет** ни на геймплей, ни на релизную сборку, ни на
веб-экспорт — это диагностика debug-рантайма. Но правило проекта «0 ERROR в
логе» он нарушает, поэтому:

- в отчёте называть лик явно и помечать как гонку, а не молча пропускать;
- **не** пытаться чинить его из GDScript: проверено, не держится (§24.5);
- **не** считать прогон красным из-за одной этой строки, если геймплей зелёный
  (`level finished: true`, `min y` в норме, 0 ошибок кроме неё).

### 24.5 Чем этот лик НЕ лечится (измерено на Bubble Peaks)

Причина известна точно: течёт музыкальная дорожка. Проверяется на голом
`--headless --quit` — **без геймплея, без харнесса**:

```bash
godot --headless --verbose --quit > _v.log 2>&1
grep -E "Leaked instance|Resource still in use" _v.log
# -> AudioStreamPlaybackOggVorbis / OggPacketSequencePlayback / OggPacketSequence
#    res://assets/audio/music/theme.ogg
```

A/B: закомментировать `Sfx.play_music("theme", 2.5)` в `main.gd::_ready()` —
счётчик становится **0/0 всегда**. То есть это не накопление и не геймплей, а
плейбек, который аудио-поток освобождает асинхронно, уже после того как движок
отчитался о вычистке кэша ресурсов.

Что пробовалось в `audio_manager._notification(NOTIFICATION_EXIT_TREE)`:
`stop()` + `stream = null` у обоих музыкальных плееров, плюс `_music_cache.clear()`
и `_sfx_cache.clear()`. **Не работает** — 5 из 6 прогонов без `--verbose` всё равно
текут. Правка откачена: мёртвый код хуже, чем его отсутствие.

Две грабли, на которых легко обмануться:

1. **`AudioStreamPlayer::stop()` в этот момент — пустышка.** Он начинается с
   `if (!is_inside_tree() || !stream.is_valid()) return;`, а на `EXIT_TREE` узел уже
   вне дерева. Вызов молча ничего не делает; лик-лист остаётся байт-в-байт тем же.
2. **`--verbose` маскирует гонку.** Замер: без `--verbose` — 6/6 текут, с
   `--verbose` — 1/6. Если мерить только с `--verbose`, легко принять случайную
   удачу за починенный баг. Мерить **без** `--verbose` и **минимум 5 раз**:

```bash
for i in 1 2 3 4 5; do godot --headless --quit > /tmp/s.log 2>&1; \
  printf "%s " "$(grep -c 'still in use at exit' /tmp/s.log)"; done
```

## 25. Браузерные прогоны тоже глушить

Правило «тестовые прогоны без звука» распространяется и на веб. На десктопе
хватает `-- --mute`, но **в вебе `index.html?--mute` не работает**: веб-шелл
Godot не пробрасывает query string в аргументы движка, `get_cmdline_args()` пуст,
в консоли 0 упоминаний `muted`. Нужен явный приём флага из адресной строки —
код и подробности в скилле `godot-headless-assets` §20.4.

Проверка, что заглушилось: в консоли браузера `[Sfx] muted (--mute)`. Консоль
читать из файла `.playwright-mcp/console-*.log` (инструмент консоли может
вернуть 0 сообщений — страница сбрасывается между вызовами MCP).

Порядок для веб-теста: `?mute` (или `?mute&cam=...&look=...`, если нужен
фиксированный ракурс) в URL.

### Водить сборку без человека: синтетические клавиши

Мышь в браузере не отдать (указатель захватывается только из жеста), а вот
клавиатуру — можно, и этого хватает, чтобы дойти до нужного места и снять кадр:

```js
const t = document.querySelector('canvas') || window;
t.dispatchEvent(new KeyboardEvent('keydown', {code: 'KeyW', bubbles: true}));
// ... подождать, потом keyup тем же code ...
```

Godot веб читает **`event.code`** (`KeyW`, `KeyD`, `Space`), а не `key`/`keyCode`.
Держать долго нельзя — `browser_press_key` жмёт и сразу отпускает, поэтому
keydown/keyup рассылать вручную через evaluate, а между ними `wait_for`. Считать
дистанцию: 6 м/с, так что 1.7 с — это ~10 м, и с края острова (радиус 9.5) легко
улететь в пустоту. Перед кадром обязательно `keyup`, иначе игрок продолжит бежать
пока идёт сама съёмка.

Признак, что ввод дошёл: игрок в кадре сдвинулся. Признак, что не дошёл: кадр
идентичен предыдущему.

## 26. Headless ≠ окно: «сцена запущена, а окна нет» — это не баг

Симптом от пользователя: «запусти Main.tscn» → агент рапортует `ok: true`,
`errors: []` → «но я так и не увидел сцену запущенную». Ни агент, ни инструмент
не врут: прогон с `--headless` **по определению окна не открывает** — он нужен,
чтобы поймать ошибки парсинга/рантайма в stdout. Пользователь ждал другого.

**Правило: у headless-прогона и у «показать игру» разные задачи, и это надо
проговаривать явно, а не считать само собой понятным.**

- Headless (`playtest.tscn`, `audit.tscn`, любой `run_scene`-инструмент) — логика.
- Окно — только запуск **без** `--headless`:
  `"<godot>" --path "<proj>" [res://Scene.tscn]`.

Отличить одно от другого можно по строке, которой headless не печатает:

```
Vulkan 1.4.325 - Forward+ - Using Device #0: NVIDIA - NVIDIA GeForce RTX 2060 SUPER
```

Есть она — рендерер реально инициализирован, окно есть. Нет — headless.

**Чего НЕ надо делать в ответ на такую жалобу:** объяснять, что
`N ObjectDB instances were leaked at exit` / `N resources still in use at exit` —
«некритично». Это правда (§24), но пользователь спрашивал не про лик, а про окно.
Отвечать надо на заданный вопрос.

### Как доказать, что окно реально видно (из оболочки агента)

`tasklist /V` показывает `Not Responding` для Godot, запущенного из оболочки
агента. **Это артефакт, а не зависание** — проверено на чистом проекте без единого
аддона: тот же статус, при этом CPU-время растёт (9→13→16 с за 6 с) и в кадре идут
счётчики. Статусу не верить.

Единственное честное доказательство — **скриншот, который смотрит сам агент**:

```powershell
Add-Type -AssemblyName System.Windows.Forms, System.Drawing
$b = [System.Windows.Forms.SystemInformation]::VirtualScreen
$bmp = New-Object System.Drawing.Bitmap($b.Width, $b.Height)
$g = [System.Drawing.Graphics]::FromImage($bmp)
$g.CopyFromScreen($b.Left, $b.Top, 0, 0, $bmp.Size); $g.Dispose()
$bmp.Save("<repo>\logs\_screen.png", [System.Drawing.Imaging.ImageFormat]::Png); $bmp.Dispose()
```

PNG читается как картинка — видно и заголовок окна, и счётчик кадров в углу.

Четыре грабли запуска GUI из оболочки агента:

1. **`run_in_background: true` + `dangerouslyDisableSandbox: true`.** В песочнице
   окно живёт ~13 с и его снимает песочница — прогон «завершается» сам, а окно
   пропадает.
2. **`FindWindow` окно НЕ находит** (разные desktop'ы), а
   `Get-Process | MainWindowTitle` — находит. Для проверки брать второе.
3. **Окно открывается ПОД уже развёрнутым окном.** Показываешь пользователю —
   без подъёма наверх он снова скажет «ничего не видно», то есть инструмент
   сработал, а задача не решена. И тут есть ловушка: **`ShowWindow(SW_RESTORE)`
   + `BringWindowToTop` + `SwitchToThisWindow` + `SetForegroundWindow` НЕ
   достаточно** — `SetForegroundWindow` из фонового процесса Windows молча
   игнорирует (лишь мигает кнопкой на панели задач), право на смену фокуса есть
   только у foreground-процесса. Проверено: окно так и осталось под Telegram.

   Рабочий рецепт — сначала прямой вызов, а при отказе `AttachThreadInput`
   к потоку текущего foreground-окна (тогда система считает вызывающего «своим»):

   ```python
   user32.ShowWindow(hwnd, 9)                       # SW_RESTORE
   user32.SetWindowPos(hwnd, 0, 0, 0, 0, 0, 0x0001 | 0x0002 | 0x0040)
   user32.BringWindowToTop(hwnd)
   if not (user32.SetForegroundWindow(hwnd)
           and user32.GetForegroundWindow() == hwnd):
       our = kernel32.GetCurrentThreadId()
       fg_thread  = user32.GetWindowThreadProcessId(user32.GetForegroundWindow(), None)
       tgt_thread = user32.GetWindowThreadProcessId(hwnd, None)
       for th in (fg_thread, tgt_thread):
           if th and th != our:
               user32.AttachThreadInput(our, th, True)
       user32.BringWindowToTop(hwnd)
       user32.SetForegroundWindow(hwnd)
       user32.SetFocus(hwnd)
       for th in (fg_thread, tgt_thread):            # обязательно отсоединиться
           if th and th != our:
               user32.AttachThreadInput(our, th, False)
   ```

   **Возвращать надо результат ПРОВЕРКИ** (`GetForegroundWindow() == hwnd`), а не
   факт вызова API — иначе отчёт «окно поднято» будет ложью. Окну нужно время
   стать готовым к переключению, поэтому попыток несколько с паузой ~0.4 с.
   Проверено скриншотом: с `AttachThreadInput` окно игры вышло поверх мессенджера.
4. **CPU-время процесса — самый дешёвый признак жизни.** Снимать `tasklist` дважды
   с паузой: растёт — игра идёт; стоит на месте при `Not Responding` — тогда
   действительно зависла.

### В лаунчере проекта

Держать отдельный `.cmd` (у нас `play.cmd`), который берёт проект из
`data/active_project.txt` и запускает `Godot.exe --path <проект> [сцена]` без
`--headless`, плюс режим `editor`. Разбор аргументов проверять **заглушкой**
(`stub_godot.cmd`, печатающий `%*`), а не открытием окна: тест идёт секунды и не
мигает на экране пользователя.

Но `.cmd` — это для человека, который сам сидит за машиной. **Если агент должен
уметь «показать» по просьбе, нужен отдельный инструмент** (`godot_play_scene` /
`godot_stop_play`): запуск `DETACHED_PROCESS` + `CREATE_BREAKAWAY_FROM_JOB`, ожидание
окна через `EnumWindows` по PID, подъём наверх, PID в файле состояния. Возвращать
`window_opened` / `window_title` / `brought_to_front` как проверенные факты.
Правило то же, что и везде: шага нет в тулчейне — 9B-модель не спросит, а начнёт
перебирать; лечится добавлением инструмента, а не правкой промпта.

И проверять **весь путь** (gateway → дочерний сервер → WinAPI), а не модуль
напрямую: клиент к `policy_gateway` показывает, что инструмент реально виден
модели в `tools/list`, а скриншот — что окно действительно на экране.

Грабля batch, на которой легко потерять полдня: `echo %VAR% | findstr /i /e ".tscn"`
**не матчится никогда** — пробел перед `|` попадает в вывод `echo`, строка
заканчивается пробелом, а `/e` привязан к концу строки. `echo %VAR%| findstr ...`
(без пробела) работает. Надёжнее вообще без pipe: `if /i "%~x1"==".tscn"`.
