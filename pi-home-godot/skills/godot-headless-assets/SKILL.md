# Godot headless: реорг ассетов и проверка ссылок

## 0. Главная грабля: `APPDATA` в песочнице

Godot на Windows берёт user-data-dir из переменной окружения `APPDATA`
(`OS_Windows::get_data_path()` → `get_environment("APPDATA")`).
В песочнице WorkBuddy `APPDATA` **не проброшена**, поэтому путь резолвится
в относительный `./Godot` и в корне проекта появляется мусорная папка:

```
<project>/Godot/{editor_settings-4.7.tres, app_userdata/, export_templates/, Godot/}
```

Симптомы: экспорт падает с
`Шаблоны экспорта не найдены по ожидаемому пути: ./Godot/export_templates/4.7.2.stable/web_nothreads_release.zip`,
а `--import` создаёт эту папку заново.

**Лечение — всегда экспортировать переменную перед вызовом Godot:**

```bash
export APPDATA="C:\\Users\\<user>\\AppData\\Roaming"
```

После этого шаблоны берутся из `%APPDATA%\Godot\export_templates\4.7.2.stable`
(проверить: `ls "C:/Users/<user>/AppData/Roaming/Godot/export_templates/"`).
Если папка `<project>/Godot` уже есть — это мусор, удалять (`du -sh` покажет ~3 МБ;
шаблоны в неё не входят, `export_templates` там пустой).

## 1. Порядок работ при переезде ассетов

1. **Бэкап** удаляемого в zip **рядом** с проектом (не внутри!) + `zipfile.testzip()`
   ДО удаления. Только потом `shutil.rmtree` / `os.remove`.
2. Правки путей: сцена, скрипты (`preload`/`load`/константы), `export_presets.cfg`.
3. `.gdignore` на папки, которые Godot не должен импортировать.
4. Удалить `.godot/uid_cache.bin`.
5. `godot --headless --path <proj> --import`
6. verify-скрипт на null-текстуры (см. §4).
7. `godot --headless --path <proj> --export-release "Web" "web/index.html"`
8. Смоук в браузере (Playwright), проверить `browser_console_messages level=error`.

## 2. uid vs path — почему сцена «не подтягивает» после переезда

При переносе `.png`/`.ogg` **`.import`-файлы теряются** (их надо переносить вместе
с ассетом!), и Godot выдаёт файлу **новый `uid://`**. Если в `.tscn` оставить
старый `uid="uid://..."`, загрузчик может пойти по мёртвому uid.

**Лечение: снять `uid` у переехавших `ext_resource`** — тогда резолв строго по
`path` (Godot допишет новый uid при сохранении сцены):

```
[ext_resource type="Texture2D" path="res://Shrooms/level_0/house.png" id="7_lgr22"]
```

Плюс удалить `.godot/uid_cache.bin` (пересоберётся из `.import` при следующем скане).

Сцены удобнее **перезаписывать целиком** (`Write`), а не править 6 раз одним
`Edit` — параллельные/повторные правки одного файла теряются.

## 3. `.gdignore` — что им закрывать

| Папка | Зачем |
|---|---|
| Сырые исходники (`.blend`, `.mp4`, `.rar`, ChatGPT-картинки) | Godot их импортирует и раздувает `.godot` (видели 356 МБ) |
| Папка сборки (`web/`) | иначе Godot импортирует свою же сборку и сыпет `web/*.import` |
| Raw-кадры персонажей, из которых печётся спрайтшит | 40 PNG × 2 персонажа = 58 МБ кэша, в игру идут только запечённые кадры |

```
# web/.gdignore
# Godot: папка сборки исключена из импорта проекта (это выход экспорта, не ассеты).
```

Проверка эффекта: `du -sh .godot/` до и после; в папке сборки не должно быть `*.import`.

**Важно:** `.gdignore` НЕ удаляет уже созданный кэш и НЕ удаляет `*.import` внутри папки.
После его установки обязательно: (1) `--import`, (2) `python tools/prune_import_cache.py`
(см. §12), (3) вручную снести `*.import` внутри закрытой папки — иначе они остаются мусором.

**`.gdignore` + `.gitignore` идут парой.** Если папка закрыта правилом `/Shrooms/*`,
то сам маркер тоже окажется игнорируемым и не попадёт в репозиторий. Нужен whitelist
в том же стиле, что уже есть для других папок:

```gitignore
!/Shrooms/characters/
/Shrooms/characters/*
!/Shrooms/characters/.gdignore
```

Проверка, что маркер попадёт в индекс: `git ls-files --others --exclude-standard Shrooms/characters/`
должен вывести ровно `Shrooms/characters/.gdignore`.

## 4. verify-скрипт: все ли ассеты сцены резолвятся

`extends SceneTree` + `_initialize()` (НЕ `_init` — тот отрабатывает слишком рано),
обход дерева, `texture.resource_path` у `Sprite2D`, `sprite_frames` у `AnimatedSprite2D`.
Готовый файл — `tools/debug/verify_assets.gd` в проекте `shrooms_2D`.

```bash
godot --headless --path <proj> --script res://tools/debug/verify_assets.gd
```

Не вызывать `get_path()` у узлов вне дерева — сыпет
`Cannot get path of node as it is not in a scene tree`; печатать имя узла или
сначала `root.add_child(...)`.

Быстрая проверка «сцена грузится без ошибок» (без скрипта):

```bash
godot --headless --path <proj> --quit-after 20 2>&1 | grep -viE "^\[|Godot Engine|^$"
```

Warning `ObjectDB instances were leaked at exit` / `resources still in use at exit`
при `--quit-after` — норма, не ошибка.

## 5. `export_presets.cfg` — не забыть про `export_files`

При `export_filter="resources"` в пресете есть **явный список**:

```
export_files=PackedStringArray("res://Main.tscn", ..., "res://Shrooms/level_0/house.png", ...)
```

Если пути переехали, а список старый — экспорт молча теряет ассеты.
Правится вручную вместе с путями в сцене.

Полезно: плагин godot_ai на экспорте сам вырезает autoload `_mcp_game_helper`
из пака (`MCP | export: stripping autoload/_mcp_game_helper from the exported pack`).
**НО** это снимает только регистрацию autoload — сам файл остаётся в паке,
если он явно перечислен в `export_files`. То есть если убрать
`res://addons/godot_ai/runtime/game_helper.gd` из списка, бут не сломается
(autoload и так вырезан), а пак похудеет. В shrooms_2D: −28.8 КБ.

Родственная грабля: `preload()`-зависимости скрипта, перечисленного в
`export_files`, в пак НЕ добавляются. Для game_helper это безвредно (он в
экспорте не инстанцируется), но если такой скрипт должен реально работать
из пака — его preload-цели надо дописать в `export_files` руками.

### 5.1 Как проверить сборку, не открывая браузер

Лог экспорта `savepack | Storing File: res://...` — это и есть манифест пака,
его достаточно грепнуть:

```bash
godot --headless --path . --export-release "Web" web/index.html 2>&1 \
  | grep -E "Storing File: res://(scenes/enemy|scripts/enemy|assets/sprites/enemy)"
```

Бут самой сборки без браузера (ловит битые autoload/скрипты/ресурсы):

```bash
godot --headless --main-pack web/index.pck --quit-after 5
```

Чисто = только баннер движка + warning'и `ObjectDB instances were leaked at exit`
(это норма для `--quit-after`, не ошибка сборки).

**Чего делать НЕ надо:** искать имена функций/констант ASCII-сканом по
`index.pck`. Пути в директории пака лежат открытым текстом (по ним искать
можно), а вот содержимое скриптов — binary tokens, идентификаторов в
открытом виде там нет. `can_stomp`, `PATROL_RIGHT_NEAR` дают 0 совпадений
даже в заведомо корректной сборке.

**Исключение из этого правила — имена действий ввода.** Они едут не в `.gdc`,
а в упакованных настройках проекта как StringName, поэтому ASCII-скан по ним
РАБОТАЕТ. Проверка, что новое действие доехало в сборку, — сравнить счётчики
с заведомо рабочими действиями:

```bash
for a in move_left move_right jump interact heal; do
  printf "%-11s %s\n" "$a" "$(grep -a -c -- "$a" web/index.pck)"
done
# ожидаем по 1 совпадению на каждое; 0 у нового действия = оно не в паке
```

Дополнительно: `Input.is_action_just_pressed("нет_такого")` в Godot 4 — это
`ERR_FAIL_COND_V_MSG`, то есть нативный прогон сцены с чистым логом уже
доказывает, что действие резолвится (но только если строка реально исполнилась:
в сцене со стартовым меню дерево на паузе и `_physics_process` игрока не идёт).

## 6. `.gitignore` whitelist для тяжёлых ассетов

Схема «игнорировать папку целиком, кроме нужных файлов» требует **снятия `!`
с самой папки**, иначе негейты по файлам не работают:

```gitignore
/Shrooms/*
!/Shrooms/level_0/
/Shrooms/level_0/*          # <- БЕЗ "!" — иначе затащит всё содержимое
!/Shrooms/level_0/*.png
!/Shrooms/level_0/*.png.import
```

Типичная ошибка: `!/Shrooms/Sounds/*` (с восклицанием) — un-ignores **все** файлы
папки, и в коммит уезжает лишнее. Проверка:

```bash
git check-ignore -q <path>; echo $?   # 0 = игнорируется, 1 = НЕ игнорируется
git ls-files <dir>                    # что реально в индексе
```

Переименование папок git может показать как `R mid_layer.png.import -> far_back.png.import`
(эвристика rename detection) — на корректность дерева не влияет.

## 7. Инвентаризация: что в проекте реально мёртвое

Наивный `grep` по basename даёт ложные срабатывания. Рабочий рецепт (Python):

```python
pat = re.compile(r"(?<![\w-])" + re.escape(name) + r"(?![\w-])")
```

**Грабли regex:** если в lookbehind добавить `/` и `.` (казалось бы, логично —
«граница пути»), то `res://assets/sprites/wizard/idle_00.png` **не находится**,
и весь используемый набор кадров уезжает в отчёт как мёртвый. Слэш и точку
в lookbehind не включать, а `_` оставить — иначе `walk_01.png` ловится внутри
`ded_walk_01.png`.

**Что ещё портит отчёт:**
- `.import`-файлы и `web/index.pck` содержат имена ассетов → исключать из корпуса.
- `tools/import_from_gdevelop.js` (маппинг имён из старого движка) держит
  ссылки на ассеты, которые игра давно не грузит. Проверять такие файлы
  отдельно: если имя встречается ТОЛЬКО там — ассет мёртвый.
- Скрипты-генераторы (`bake_*.py`) держат ссылки на **исходники**, а не на
  результат — не считать их доказательством использования.

**Дубли** искать по md5 среди всех файлов (в т.ч. в папках-архивах исходников):
часто «мёртвый» ассет оказывается байт-в-байт копией используемого.
Индексировать по размеру, потом сверять хеш — на сотнях PNG быстрее.

**Осиротевшие `.import`** (исходник удалён, `.import` остался) — отдельная
проверка; Godot их не чистит сам. Скрипт: для каждого `*.import` проверить
существование файла без суффикса.

**Порядок:** бэкап (см. §1) → удаление → `--import` → verify-скрипт (§4).
Откат удалённых ассетов, если они были в git: `git checkout <commit> -- assets/`.

## 9. Смоук web-сборки в Playwright (шаг 8 из §1)

**Сервер:** свой статик, не `http.server` (нужны правильные MIME для `.wasm`):
```bash
cd <proj> && python tools/web/serve.py --dir web --port 8791
```
Проверка живости: `curl -s -o /dev/null -w "http=%{http_code}" http://127.0.0.1:8791/index.pck` → 200.

**Вьюпорт строго 1280x720** (`browser_resize`) + reload. Тогда
`canvas.width/height == canvas.getBoundingClientRect() == viewport`, леттербокса нет
и координаты кликов мапятся 1:1 в игровые пиксели. При произвольном вьюпорте Godot
леттербоксит: `scale = vh/720`, `xoff = (vw - 1280*scale)/2`, и клик уезжает.

**Чёрные полосы по краям окна — это `window/stretch/aspect`.** При
`mode="canvas_items"` дефолт аспекта — `keep` (леттербокс): на 1920x897
(2.14:1 против 16:9 проекта) игра показывала полосы слева и справа. Лечится
одной строкой:

```ini
window/stretch/mode="canvas_items"
window/stretch/aspect="expand"
```

`expand` заполняет окно всегда, показывая больше мира по широкой стороне.
Проверка в браузере: `canvas.width/height == getBoundingClientRect() ==
window.innerWidth/Height`, плюс скан краёв скриншота на тёмные пиксели (норма —
единицы процентов, это сам арт; полоса даёт 100% по всей колонке).

**Клик по canvas:** у `browser_click` нет параметра координат → только
`browser_run_code_unsafe`:
```js
async (page) => { await page.mouse.move(640, 479); await page.waitForTimeout(300);
  await page.mouse.click(640, 479, { delay: 80 }); }
```
Перед кликом — `page.mouse.move`, Godot обрабатывает hover/hit.

**Ввод с клавиатуры:** `page.keyboard.down('d')` / `' '` — мапится в physical_keycode
(`D`=68, `Space`=32), совпадает с `[input]` в `project.godot`.

**Загрузка:** ~20 с до первого кадра (wasm 38 МБ). Ждать промисом внутри
`browser_evaluate`, а не `browser_wait_for` — иначе MCP роняет контекст
(`Target page, context or browser has been closed` → `No open pages available`;
лечится повторным `browser_navigate`).

**Что считать успехом:**
- `browser_console_messages level=warning all=true` → 0 error / 0 warning.
  Норма в логе: баннер `Godot Engine vX`, `OpenGL ES 3.0 (WebGL 2.0)`, `Emscripten ...`.
- `performance.getEntriesByType('resource')` → все `responseStatus == 200`
  (проверяет `.js/.wasm/.pck/.icon.png`).
- Скриншот меню и уровня; прожать движение/прыжок и сверить, что спрайт сместился.

**Уборка:** артефакты `shots/` и `.playwright-mcp/` держать в `.gitignore`
(проверка: `git check-ignore -q <path>`). `browser_take_screenshot` с **относительным**
`filename` кладёт PNG в корень проекта. После теста: `browser_close`, `TaskStop` сервера,
контроль `curl ... -m 2 -w "http=%{http_code}"` → `000` (connection refused).
Не гасить чужие `python.exe` — только свой сервер по `task_id`.

### 9.1 Почему в браузере нельзя проверять геймплей

Godot web режет физику по `physics/common/max_physics_steps_per_frame` (по умолчанию 8).
Если рендер в браузере медленный (в песочнице — software-ный WebGL), fps падает ниже
7.5, шаги физики отбрасываются, и **игра идёт медленнее реального времени**: замерено
~35 px/s вместо 190 при вьюпорте 1280x720 и ~76 px/s при 640x360. Пройти уровень
«ходьбой» нереально. В браузере проверять только: загрузку, меню, HUD, консоль
(`browser_console_messages level=warning all=true` → 0 error), HTTP-коды ресурсов.
Наличие ассетов в сборке — грепом строк по `web/index.pck`:
`python -c "print(b'sprites/enemy/walk_00.png' in open('web/index.pck','rb').read())"`.

## 10. Нативные скриншоты и логические тесты (без web-сборки)

Глазами проверять итеративно быстрее нативно: `--headless` рендер не умеет
(dummy-драйвер), но обычный запуск окна работает и на машине без «дисплея».

`tools/debug/shot.gd` — `extends SceneTree`, грузит `Main.tscn`, гасит стартовое
меню (`gf.set("_menu_done", true)` до инстанцирования), ставит игрока/врага,
ждёт N кадров, пишет `root.get_texture().get_image().save_png(...)`:

```bash
godot --path . --script res://tools/debug/shot.gd -- \
      --out=имя --frames=30 --px=3400 --py=300 --edir=0 --ex=3400 \
      --count=9 --every=2
```

Ключевые приёмы:
- **Серию кадров снимать в ОДНОМ процессе** (`--count/--every`). Отдельные запуски
  недетерминированы: враг/физика успевают уехать на разное число кадров, и
  «поймать» анимацию расплющивания (0.16 с) невозможно.
- **Телепорт требует сброса камеры**: `cam.position_smoothing_enabled = false;
  cam.reset_smoothing()`, иначе камера едет полсекунды.
- **Первый кадр после телепорта врёт**: `is_on_floor()` ещё держит прошлое
  значение, поэтому объект не падает один кадр. В тестах давать `await physics_frame`
  и только потом считать.
- `--` перед своими аргументами обязателен, читать их `OS.get_cmdline_user_args()`;
  голые `--w/--h` НЕ переопределяют размер, если в `project.godot` задан
  `window/stretch/mode` — размер окна задавать через `root.size` + `--resolution`.

**Три грабли, которые стоили часа отладки:**

1. **`float("nan")` в GDScript == 0.0**, а не NaN (`String.to_float()` парсит
   префикс и на мусоре возвращает ноль). Если необязательный аргумент читать как
   `float(_arg("ex", "nan"))`, то непереданный `--ex` молча телепортирует объект
   в x=0, а `--edir` обнуляет направление — и враг «исчезает из кадра», хотя на
   самом деле стоит в нуле. Ловить отсутствие по пустой строке:
   ```gdscript
   func _farg(name: String) -> float:
       var s: String = _arg(name, "")
       return NAN if s.is_empty() else s.to_float()
   ```
2. **Ждать `await physics_frame`, а не `process_frame`.** В headless/idle цикл
   крутится на максимальной частоте: «900 кадров» через `process_frame` давали
   меньше двух секунд игры, и враг просто не успевал дойти. Физика всегда 1/60 с
   → `--frames` становится детерминированным числом игровых секунд.
3. **`_report` не должен принимать freed-объект в типизированный параметр** —
   `Invalid type in function '_report' ... (previously freed)`. Если за время
   прогона врага расплющили, скрипт падает, `quit(0)` не вызывается и процесс
   висит до таймаута. Передавать `enemy if is_instance_valid(enemy) else null`.

И вообще: **всегда печатать, что реально попало в кадр** — позицию игрока, врага
и границы кадра из `camera.get_screen_center_position()`. Без этого смотришь
скриншот и не понимаешь, почему врага не видно (камера с лимитами уезжает не
туда, где ждёшь).

4. **Оконный прогон `shot.gd` может поймать РЕАЛЬНЫЙ ввод.** `--headless` рендер
   не умеет, поэтому скриншоты снимаются настоящим окном — а окно в фокусе
   принимает клавиатуру. Один раз это дало кадр, который невозможно объяснить:
   игрок оказался ровно в `DOOR_POS`, спрайт исчез (твин «засасывания в дом»),
   враг расплющен. Твин требует нажатия F — без ввода игрок туда попасть не мог.
   **Правило: если кадр выглядит невозможным — сначала прогнать 3 раза подряд,
   и только если повторяется, лезть в код.** Три прогона дали байт-в-байт
   одинаковый результат, аномалия была разовой.

### Снять HUD (полоски, счётчики) крупным планом

HUD живёт в `CanvasLayer` (экранные координаты), поэтому снимается тем же
`shot.gd`, но с кропом угла экрана и увеличением:

```bash
godot --path . --script res://tools/debug/shot.gd -- \
      --out=hud --frames=60 --px=2000 --py=464 \
      --hp=2 --mush=3 --crop=10,10,190,75 --zoom=4
```

- `--crop=x,y,w,h` — `Image.get_region(Rect2i)`, `--zoom=K` — `Image.resize` с
  `INTERPOLATE_NEAREST`. Без NEAREST пиксельные иконки размываются и по ним
  нельзя понять, где кончается заливка сегмента.
- `--hp/--mush` не «молча пишут в поля», а **эмитят те же сигналы**, что игра
  (`hp_changed`, `mushrooms_changed`): иначе HUD о подмене не узнает и снимет
  полоску со старыми числами. Значения полоски анимируются (`_shown` догоняет
  `_hp` за ~0.6 с) → давать `--frames=60`, иначе на кадре «перетекающий» сегмент.
- **Ставить игрока ВНЕ пикапов и триггеров.** Телепорт в точку подбираемого
  предмета срабатывает как настоящий подбор прямо во время съёмки: выставленное
  `--hp=1` на кадре превращается в 2, потому что гриб честно вылечил. Это не баг
  отрисовки, а живая демонстрация геймплея - но кадр «врёт» относительно флагов.
  Если кадр не сходится с выставленными числами - искать рядом `Area2D`.

`tools/debug/test_enemy.gd` — логический тест в `--headless` (коллизии и физика
работают без рендера). Схема: свежая сцена на каждый кейс, `_spawn()` + `_step(n)`
через `await physics_frame`, `_ok(имя, условие, детали)`, счётчик провалов,
`quit(1 if _fails else 0)`.

Грабли при написании таких тестов:
- Не проверять «отскок» по `velocity.y < 0` — откидывание от урона тоже
  отрицательное. Порог должен различать эффекты (отскок −380 против урона −300).
- Не ронять игрока и врага одновременно: оба упадут рядом. Сначала дать встать
  на пол (`_step(20)`), потом поднять игрока и уронить на голову.
- Проверка «стоит на полу» должна учитывать рельеф: пол в коридоре гуляет
  558..592, поэтому `max_y - min_y < 50`, а не `< 10`.
- **Спавнить игрока только в пустой геометрии.** Внутри коробки платформы его
  выталкивает на десятки пикселей — прямо на голову врагу, враг честно
  расплющивается, и тест начинает врать («враг исчез, хотя не должен»).
  Если игрок в кейсе нужен только как метка координаты X, морозить его
  (`set_physics_process(false)`) и поднимать в воздух: заодно `take_damage`
  выходит по `is_physics_processing()` и HP не портится.
- **Разворот на границе патруля проверять счётчиком сбросов паузы.**
  Если условие границы не смотрит на направление, `_turn()` зовётся повторно на
  том же месте: направление то же (`dir_changes` не растёт!), а пауза сбрасывается
  заново — враг стоит ~1 с вместо 0.28 с и «буксует» ногами. Ловится так:
  число ВОЗРАСТАНИЙ `_pause` должно быть РАВНО числу смен направления.
- **Стоящий враг не наносит урона.** Проверка контакта идёт по перекрытию
  `Area2D` с коробкой игрока: враг, поставленный в 28 px и с `_dir = 0.0`,
  НЕ перекрывается с ней, и кейс «урон при касании» даёт 0 урона. Рабочий
  рецепт (из `test_enemy._case_damage`): вести врага НА игрока, `_dir = -1.0`,
  и давать ~45 кадров. Симптом ошибки - «HP не изменилось», а не падение теста.
- **Нажатие клавиши в headless проверяется через `Input.action_press()`, но
  ждать надо ДВА `await physics_frame`.** Сигнал `physics_frame` эмитится ДО
  `Node._physics_process`, поэтому при одном ожидании проверка успевает раньше
  самого узла и кейс ложно падает («HP не изменилось»). Заодно проверять
  `InputMap.has_action("имя")` - это ловит действие, не доехавшее до
  `project.godot` (например, если редактор затёр файл своим сохранением).

## 10.1 Перекрытие `Area2D` приходит на кадр позже

Самая дорогая грабля геймплея. `get_overlapping_bodies()` и сигнал
`body_entered` отражают состояние **предыдущего** физического шага, а
`_physics_process` узлов идёт после `move_and_slide()`. Итог: игрок падает на
врага, за кадр до этого приземляется на его коллизию (`velocity.y` → 0), и
только на СЛЕДУЮЩЕМ кадре приходит перекрытие. Любая проверка «падал ли игрок»
по одному кадру (`prev_velocity_y > 0`) в этот момент уже false → прыжок сверху
засчитывается как боковой удар: игрок теряет HP, враг живёт. Симптом у
пользователя звучит как «иногда прыгаю сверху, а урон получаю я».

Лечится **окном**, а не одним кадром:
```gdscript
const FALL_GRACE: float = 0.15          # 9 кадров запаса
const STOMP_RISE_MAX: float = 60.0      # выше этого подъёма - не «сверху»
var _fall_grace: float = 0.0
# в _physics_process:
if velocity.y > 0.0: _fall_grace = FALL_GRACE
else:                _fall_grace = maxf(0.0, _fall_grace - delta)

func can_stomp() -> bool:
    return _fall_grace > 0.0 or velocity.y > -STOMP_RISE_MAX
```
`velocity.y > -STOMP_RISE_MAX` закрывает второй случай — игрок уже СТОИТ на
коробке врага, падения нет вообще; при этом взлетающий вверх (−450) врага не
расплющивает, а бьётся об него.

**Регрессионный тест обязателен и должен падать на старом коде.** Ставить
игрока ступнями ровно на верх коробки врага, обнулять `velocity`,
`prev_velocity_y` и `_fall_grace`, морозить физику игрока — и требовать, чтобы
враг исчез. Проверять, что тест реально ловит баг: временно вернуть старое
условие и убедиться в FAIL, иначе тест ничего не гарантирует.

## 11. Запекание кадров нового персонажа (bake_*_frames.py)

Исходники из генератора нельзя класть в игру: фон с alpha-шумом, холсты
разного размера, десятки МБ. Рецепт (по образцу `tools/bake_wizard_frames.py`,
для врага — `tools/bake_enemy_frames.py`):

1. `arr[arr[:,:,3] < 24] = (0,0,0,0)` — шум генератора (alpha 2..12) иначе даёт ореол.
2. **Период цикла искать автокорреляцией**, а не на глаз: уменьшить кадры до
   ~28x26, посчитать `mean(abs(st[:n-p] - st[p:]))` для p = 6..n/2, взять минимум.
   Для 40 кадров врага минимум на p=12 (стык 1.86), т.е. 40 = 3 цикла + 4 лишних.
3. Взять окно `period` кадров с минимальным различием `frame[s]` и `frame[s+period]`.
4. Якорь: `cx_feet` (центр масс нижних `FEET_BAND` высоты силуэта). Сдвиг —
   **ОДИН общий на всю анимацию** (`legs_avg`), и для ходьбы, и для стойки.
   Покадровый якорь (каждый кадр ставится по своим ногам) выглядит логично, но
   двигает ВЕСЬ кадр вслед за покачиванием ног, а округление сдвига до целых
   пикселей добавляет скачки: на замерах худший шаг петли idle падал с ~4.8 до
   ~4.0, число резких переходов — с пяти до двух. Позиция:
   `x0 = w/2 - (anchor - bbox[0])`, `y0 = baseline - (feet - bbox[1])`;
   без вычитания `bbox[0]` спрайт дрожит.
5. Ресайз через premultiplied alpha, иначе тёмный ореол по краю.
6. `SpriteFrames` писать текстом (`[gd_resource ...]` + `ExtResource`), как
   `resources/player_frames.tres` / `enemy_frames.tres`.
7. **Печь кадры С ЗАПАСОМ над экранным размером и отдавать их под `scale`
   узла.** Раньше пекли ровно в экранный размер (scale узла = 1), и это лечило
   рябь на ходу: пока текстура 288 px ужималась на рендере в 128 (scale
   0.4449), точечная билинейная выборка без мип-уровней (`mipmaps/generate=false`,
   `compress/mode=0`) давала на каждом кадре анимации СВОЙ шум — персонаж
   «рябил» мелко на ходу, а в стойке был чёткий (дробная часть экранной
   координаты не меняется, рисунок выборки стоит на месте). Жалоба звучит как
   «идёт — рябит, стоит — чёткий, враги при этом не рябят»: искать единственный
   спрайт, который рисуется не 1:1.
   **НО** кадр ровно в экранный размер всё равно мылится — канвас в окне
   масштабируется ДРОБНО (см. §11.1). Поэтому: `BAKE_MULT = 1.25` к высоте
   персонажа + `Sprite.scale = 0.8`. Размер кадра считать не множителем, а от
   роста персонажа: `DOWNSCALE = CHAR_HEIGHT_PX / content_pre`, где
   `content_pre` — высота силуэта в канвасе, а `CHAR_HEIGHT_PX =
   CHAR_SCREEN_PX * BAKE_MULT`. Контроль: кадр 196x321 при росте на экране
   210 px, ступни на строке 315, `Sprite.position.y = -22.6`, `scale = 0.8`.
   Смещение ступней в МИРОВЫХ координатах = `drop_tex * SPRITE_SCALE`, а не
   `drop_tex`: `position.y = TARGET_FEET_PX - (feet_row - h/2) * SPRITE_SCALE`.
   `scale` узла НЕ влияет на `position` (та в координатах родителя), поэтому
   выпад/тряска, которые пишут `sprite.position`, пересчёта не требуют.
   Коллизию масштабировать вместе с персонажем (`SIZE_MULT`), низ оставлять на
   `TARGET_FEET_PX`.
8. **Петлю выбирать по ГОТОВЫМ кадрам, а не по исходникам и не по превью.**
   Метрика петли: для циклического окна `[a, a+L-1]` качество =
   `max(макс. шаг ВНУТРИ окна, шаг на ЗАМЫКАНИИ)`, ищем минимум. Считать надо
   на кадрах, наложенных на СЕРЫЙ фон (`convert("RGB")` у прозрачных пикселей
   оставляет их цвет — обычно чёрный, и метрика меряет почти только силуэт),
   и в ПОЛНОМ размере: на превью 26x45 и 72x118 скрипт дважды выбрал окно, у
   которого замыкание оказывалось ХУДШИМ шагом петли. Порядок: `render()` ->
   поиск окна по результату -> запись `SpriteFrames`.
9. **После запекания — `godot --headless --path <proj> --import`.** Bake сносит
   старые `*.png` и `*.png.import` (а они в git!), но запуск игры без редактора
   импорт НЕ делает: получаешь `Parse Error: [ext_resource] referenced
   non-existent resource at: res://assets/sprites/wizard/walk_21.png` и часть
   кадров молча не грузится. Тот же `--import` обязателен после любой правки
   набора кадров.

### 11.1 Почему «растянутый персонаж» становится мутным (дробный канвас)

`window/stretch/mode="canvas_items"` + `aspect="expand"` даёт масштаб канваса
`= высота_окна / viewport_height`. При окне 1920x897 это `897/720 = 1.2459` —
**дробное** число, поэтому ЛЮБОЙ спрайт ресемплится билинейно, даже если
нарисован 1:1. Замер энергии градиента по контуру кадра персонажа:

| текстура→экран | энергия | сохранено |
|---|---|---|
| 1:1 (эталон) | 18.12 | — |
| 1.2459 (кадр 1:1 в экранном размере) | 11.63 | 64% |
| 0.9967 (кадр 1.25x, `scale` узла 0.8) | 12.57 | **73%** |

**Лечение:** печь кадры в 1.25 раза крупнее экранного размера и опустить
`scale` узла до 0.8, чтобы `1.2459 * 0.8 = 0.9967`. Дробную часть фазы это не
убирает (период уезда ~300 px, на середине цикла 1-px детали блендятся 50/50),
поэтому 100% не будет НИКОГДА — но 73% против 64% видно глазами.

**Что НЕ работает (проверено):**
- `stretch=integer` (`Window.CONTENT_SCALE_STRETCH_INTEGER`): на 1920x897 даёт
  scale 1.0, но viewport сжимается до 1541x720 и по краям чёрные поля — ровно
  то, от чего уходили через `expand`.
- `TEXTURE_FILTER_NEAREST` на спрайте: при текстура→экран 0.9967 картинка
  неотличима от линейной, а на движении даёт «прыгающие» пиксели.
- Выставить `scale = 1/1.2459` (текстура→экран ровно 1.0): с линейным фильтром
  и дробным смещением спрайта это даёт РАВНОМЕРНЫЙ бленд 50/50 по всему кадру,
  то есть хуже, чем медленно уезжающая фаза при 0.9967.

**Цена:** на окне 1280x720 (канвас 1.0) персонаж теперь ресемплится в 0.8
(раньше был 1:1). Если играют в браузере на 1920 — компромисс оправдан.

**Чем мерить.** Оффлайновый `Image.resize` в Pillow НЕ воспроизводит выборку
Godot (у Pillow при downsample включается антиалиасинговый фильтр). Решение —
проба на живом рендере: `tools/debug/probe_sharp.gd` (в shrooms_2D) гоняет
`Main.tscn` при разных размерах окна и фильтрах, кропает спрайт и кладёт
`crop 1:1` + `zoom x4` в `shots/`. Смотреть глазами И считать.

**Знак offset у Sprite2D (частая ошибка).** `centered=true`: центр картинки
лежит на `origin + offset`. Если ступни на строке `feet_row` в картинке высотой
`h`, то `offset.y = h/2 - feet_row` (ОТРИЦАТЕЛЬНЫЙ, если ступни ниже центра).
Проверка: масштабирование узла оставляет ступни на месте — именно на этом
держится анимация расплющивания (`scale = (1.45, 0.12)` при origin на ступнях).

## 12. Чистка `.godot/imported` (память пухнет до сотен МБ)

Удаление исходника **не** удаляет его `.ctex` из кэша — Godot чистит импорт
только пока открыт редактор. У нас так накопилось 506 МБ (1723 сироты, включая
рендеры прошлого проекта: `ded_*`, `Dog_*`, `Bubbles_*`, `Cave_*`, `Mountains_*`).

**Наивный детектор сирот («имя исходника из имени ctex не встречается на диске»)
ломается на `.gdignore`**: файл-то на диске есть, а в проект больше не входит.
Правильный критерий — живые ссылки из `.import`:

```python
# tools/prune_import_cache.py (в проекте shrooms_2D)
# 1. собрать папки под .gdignore (os.walk, при нахождении .gdignore — не спускаться дальше)
# 2. os.walk по проекту, пропуская .git/.godot/ignored/shots/web
# 3. из каждого *.import вытащить dest_files=[...] -> basename'ы
# 4. удалить всё в .godot/imported, чего нет в этом множестве
```

Формат имени: `<md5>.ctex` + `<md5>.md5`, ссылка в `.import` — `res://.godot/imported/<md5>.ctex`.
Результат: 888 файлов → 74 живых, `.godot` 277 МБ → **32 МБ**. Дополнительно снести
`*.import` внутри закрытых `.gdignore`-папок (в проекте их было 169 штук) — Godot их
всё равно не читает, а воссоздаст сам, если папку снова открыть.

Порядок безопасен: если что-то живое снесли лишнего, следующий `--import` восстановит.
Всегда прогонять `--dry` перед удалением и потом `verify_assets.gd`.

**Проверка рендера врага на скриншоте без глаз.** Враг может оказаться в кадре не там,
где ожидаешь (камера с лимитами, `--px` не равен центру экрана), поэтому позицию ищут
диффом двух кадров с врагом на разных `--ex` при том же игроке:

```python
ImageChops.difference(a, b).convert('L').getbbox()
```

Pillow в managed-python НЕТ. Минимальный декодер PNG (zlib + распаковка
фильтров строк, color type 2/6, depth 8) пишется на месте за ~25 строк и
покрывает и дифф, и анализ колонок. Не тянуть `pip install pillow` ради этого.

## 12.1 ГЛАВНАЯ ЛОВУШКА: открытый редактор Godot затирает правки на диске

Редактор Godot держит сцену **в памяти**. Если он открыт, а файл `.tscn`
меняется на диске (скриптом, ассистентом, `sed`), редактор об этом не знает.
Первое же сохранение из редактора записывает ЕГО копию целиком поверх файла —
и правки с диска исчезают. У нас так пропали зеркальный тайл far-фона и узел
`EnemyLeft`, уже лежавшие в коммите.

Признаки: `git diff HEAD` показывает, что **исчезли твои же закоммиченные
правки**, а появились чужие; mtime файла свежее времени коммита.

Порядок работы:

```bash
ls -l --time-style=full-iso Main.tscn    # mtime ДО правки
# ... правка ...
ls -l --time-style=full-iso Main.tscn    # mtime ПОСЛЕ: если изменился сам
                                         # по себе — редактор сохранил
```

Если редактор открыт — предупредить пользователя: сохранять нельзя, пока он
не перечитает сцену (`Scene > Reload from disk` / переоткрыть сцену). Иначе
цикл «правка на диске → сохранение из редактора → откат» повторяется.

**И рядом:** в проектах, где пользователь работает параллельно, `git add -A`
и `git add .` запрещены — утащат в коммит его черновики. Только явные пути,
а перед коммитом `git diff HEAD -- <файл>`. У нас `git add -A` утащил
незакоммиченный эксперимент с масштабом мид-слоя и выглядел как «ассистент
сломал mid».

## 13. Шов у тайлящегося фона (Parallax2D)

Симптом: на фоне видна резкая вертикальная граница, причём «не на одном
месте» — она ползёт по экрану вместе с параллаксом.

**Причина №1 — период не равен ширине тайла.** У `Parallax2D` копии ребёнка
кладутся с шагом `repeat_size`. Если `repeat_size.x` не равен визуальной
ширине спрайта (`texture.width * sprite.scale.x`), копии либо перекрываются,
либо между ними дыра:

```
far_back.png 2170 px, scale 1.0650864  ->  визуальная ширина 2311.237
repeat_size = 2170  ->  перекрытие 141.24 px, в полосе перекрытия жёсткий обрыв
```

**Причина №2 — картинка не бесшовна по краям.** Даже с правильным периодом
левая и правая колонки тайла не совпадают (у нас: 25-40% строк, до 181 на
канал), поэтому на стыке видно «склейку».

**Как отличить здоровый тайлинг от сломанного — одно умножение:**

```
texture.width * sprite.scale.x  ==  Parallax2D.repeat_size.x   ?
```

У мид-слоя этого проекта: `2170 * 0.93389493 = 2026.5520`, а `repeat_size.x`
как раз `2026.552` — совпадает до знака, тайлится идеально, трогать нечего.
У far-фона: `2170 * 1.0650864 = 2311.2375` против `repeat_size.x = 2170` —
расхождение 141 px, вот он и был сломан. **Если равенство выполняется, баг не
здесь** — ищи в другом слое (у нас «разрывы в mid» оказались черновиком
пользователя с масштабом `0.67798203`, см. §12.1).

**Лечение — зеркальный тайлинг.** Второй тайл того же спрайта с `flip_h = true`
на расстоянии одной ширины, период = двум ширинам:

```
repeat_size = Vector2(2 * 2170 * 1.0650864, 0)   # 4622.474976
[node Sprite]        position.x = 516.5978
[node SpriteMirror]  position.x = 516.5978 + 2311.237488 = 2827.835288
                     flip_h = true
```

Тогда на каждом стыке правая колонка одного тайла встречает ТУ ЖЕ колонку
отражённого (`flip_h` отображает колонку `w-1` в колонку `0`), и совпадение
краёв картинки перестаёт требоваться вообще. Стыков в бесконечной ленте
ровно два типа — `A|A'` и `A'|A`, оба зеркальные.

Позиции считать в python и вписывать полной точностью: `2311.237488`, не
`2311.24` — на периоде в 4622 px дробная часть сдвигает тайл на глаз.

### 13.1 Как доказать, что шов снят, а не просто «стало похоже»

1. Выбрать кадр, где нужный слой ВИДЕН и не закрыт другими: у нас far-фон
   перекрыт мид-слоем (тот занимает world y 209..701), поэтому анализировать
   надо полосу чистого неба — `screen_y = world_y - cam_center_y + 360`, у нас
   строки 80..250, колонки ниже HUD (x>210) и левее иконки mute (x<1200).
2. Снять кадр в НОВОЙ конфигурации и в СТАРОЙ (временно вернуть `repeat_size`
   и убрать `SpriteMirror`, потом обязательно восстановить — проверять
   `grep -c SpriteMirror`).
3. Профиль по колонкам: `d(x) = среднее |pixel(x) - pixel(x-1)|` по строкам
   полосы. Шов — это выброс в одной колонке. Сравнивать с медианой профиля:
   шов даёт 5-7x медианы, обычная деталь туманности — до 2-3x.

Результат у нас: старая конфигурация 110..134 (до 6.6x) на границе тайла,
новая 36..87 без выброса на стыке. **Если кадры старой и новой конфигурации
идентичны — шов в этом кадре просто за кадром**, это не доказательство.
Проверять по позициям: у нас шов появлялся только при `--px >= 2500`
(параллакс 0.25 сдвигает окно фона всего на четверть пути игрока).

Мелочи, которые портят анализ: иконка mute (правый верх, x 1225..1265) и
полоса HP (левый верх, x 22..200, y 20..41) дают выбросы круче любого шва —
их колонки исключать.

bbox шириной ровно `2*ширина_спрайта - |Δx|` и высотой ≈ высота спрайта = враг на месте.

## 14. Пиксельная надпись: затухание гасить `modulate`, а не alpha в draw_rect

Симптом от пользователя: «когда исчезает, белый на прозрачный фон скачет».
То есть надпись почти не гаснет, а потом срывается.

**Причина — жирный начерк.** `pixel_font.draw_text(bold)` рисует на каждый
«пиксель» глифа прямоугольник размером `px + 2*bold`, поэтому прямоугольники
СОСЕДНИХ пикселей перекрываются. При `alpha = 1` это незаметно, но при
`alpha < 1` перекрытия складываются: точка в теле буквы закрыта ~9
прямоугольниками (окрестность 3×3) и её непрозрачность идёт как `1-(1-a)^9`,
а у внешней каймы — как `a`. При `a = 0.3` это **96% против 30%**: буквы
держатся почти непрозрачными и пропадают рывком.

**Вторая половина того же бага — тень.** Если передать в `colors`
`Color(0,0,0,0.55*a)` И одновременно `alpha = a`, то `draw_text` умножает ещё
раз, и тень гаснет как `0.55*a²` — то есть исчезает задолго до букв.

**Лечение — два шага, и второй важнее первого:**

1. Если затухание нужно, гасить его `modulate` узла, а не alpha у `draw_rect`:
   `modulate` применяется к готовому рисунку один раз, поэтому кривая линейна
   и тень держит свою долю.
2. **Но если надпись должна быть «плотной», никакой альфы быть не должно
   вообще.** Пользователь на «modulate-версии» всё равно сказал: «на мгновение
   прозрачный внутри — потом белым становится, перед исчезновением снова
   прозрачный». Любая альфа < 1 = буквы просвечивают, а задание/подсказка
   обязаны читаться плотно с первого кадра. Рабочее решение: появление и
   исчезновение одним кадром (`visible`), никакого fade-in/out, подложка
   непрозрачная, позиция статичная. Плюс `queue_redraw()` в `_process` тогда
   не нужен вовсе.

Правило общее: **любая составная пиксельная графика, которая должна гаснуть,
обязана гаснуть через `modulate`/`self_modulate`; а если по требованию она
должна быть плотной — не гаснуть, а просто включаться и выключаться.**

**Замер линейности** (`tools/debug/probe_label_fade.gd` в shrooms_2D, потом
удалён вместе с затуханием): для каждой ступени альфы снимаются ДВА кадра
подряд — с надписью и без неё (`modulate.a = 0`), — и берётся средняя |разница|
по полосе вокруг текста. Величина пропорциональна альфе. Результат был
100 / 82 / 63 / 44 / 23 / 12 / 6% против идеальных 100/80/60/40/20/10/5.
Сравнение с ОДНИМ опорным кадром так не работает: фон анимированный,
отличается 88% пикселей полосы.

## 15. Маркеры на рендере: доказать точку, а не поверить в неё

Когда координата (точка вылета снаряда, посадка ступней) вычислена формулой,
её надо подтвердить на КАДРЕ, а не пересчётом — иначе проверка тавтологична.
Рецепт (`tools/debug/probe_tip.gd`): рядом с игроком в мировых координатах
добавляется `Node2D` с `_draw()`, рисующим крестик/линию в проверяемой точке
(`z_index` выше игрока), затем снимается кадр и кроп вокруг спрайта
увеличивается `INTERPOLATE_NEAREST` в 3-4 раза.

Найденное так: `staff_tip()` = `origin + (48.8, -77.8)`, где `-77.8` =
`STAFF_TIP.y (-55.2)` + `sprite.position.y (-22.6)`. Константа меряется от
ЦЕНТРА спрайта, а `position` узла прибавляется сверху — при пересчёте точки
после перепечки кадров это легко упустить.

**Готча измерения по кадру вьюпорта:** `get_texture().get_image()` отдаёт
**RGB8** (3 байта на пиксель), не RGBA8. Шаг считать как
`band.size() / (w * h)`, а не хардкодить 4 — иначе `Out of bounds get index`.
И `Image.resize()` / `Image.convert()` возвращают void: цепочка
`img.resize(...).save_png(...)` даёт `Parse Error`.

## 16. Прогон тестов проекта и как доказать, что падение не твоё

Полный набор в shrooms_2D (`--headless`, рендер не нужен):

```bash
for t in verify_assets test_enemy test_combat test_mushroom; do
  godot --headless --path <proj> --script "res://tools/debug/$t.gd"
done
```
`verify_assets.gd` идёт через `--script` (не `.tscn`), тесты печатают
`[test] проверок N, провалов M` и `quit(1)` при провалах.

**Не докладывать «тест падает», не выяснив, твой ли это регресс.** Дешёвый
способ (полторы минуты): распаковать старый коммит БЕЗ рабочего дерева и
прогнать тот же тест там.

```bash
git archive <старый_коммит> | tar -x -C /f/.../_old      # НЕ worktree
godot --headless --path "F:/.../_old" --import           # .godot в архиве нет
godot --headless --path "F:/.../_old" --script res://tools/debug/<t>.gd
diff <(grep FAIL old.log) <(grep FAIL new.log)           # совпало = не твой
```

В shrooms_2D так выяснилось, что `test_combat` (21 падение из 68) устарел
РАНЬШЕ правок: список падений совпал строка в строку, различия только в
подпиксельных значениях. Судя по содержанию, тест не обновлён под изменения
геймплея — он ждёт `RESPAWN_TIME = 30` (в коде 10) и модель «ровно 5 зарядов»
(гриб даёт x5 и возрождается 10 раз). Живые тесты на ту же дату:
`verify_assets` 0 проблем, `test_enemy` 15/15, `test_mushroom` 23/23.

## 17. Заливка аудио из паков (SoX WAV→OGG) и почему банк «не звучит»

### 17.1 Три грабли SoX

1. **Эффекты идут ПОСЛЕ выходного файла.** `sox in.wav -C 5 gain -n -1 out.ogg`
   падает с `FAIL sox: missing filename`. Правильно: `sox in.wav -C 5 out.ogg gain -n -1`.
   `-C` (compression) — наоборот, ДО выходного файла.
2. **Нативный exe не понимает posix-путь.** Из Git Bash `$(pwd)` даёт `/f/...`,
   и SoX отвечает `can't open input file ...: No such file or directory`.
   Переводить корень: `ROOT="$(cygpath -m "$ROOT")"` → `F:/...`.
3. **`soxi` в поставке может отсутствовать.** Длительность/формат читать так:
   `sox --i -D file.wav` (секунды), `sox --i file.wav` (всё).

Смысл нормализации: музыка — обязательно `gain -n -1` (паки сведены вразнобой,
иначе трек клиппует или тонет). SFX — **нельзя**: индивидуальная нормализация
убивает относительную громкость, и шаг станет таким же громким, как дробовик.

### 17.2 ГЛАВНАЯ ловушка: `.wav` перекрывает `.ogg`

Типовой `_load_bank()` перебирает расширения в порядке `.wav → .ogg → .mp3` и
берёт **первое найденное**. Поэтому:

> Положить `jump.ogg` рядом с существующим `jump.wav` — создать файл, который
> не загрузится НИКОГДА.

Симптом, который на это наводит: «звука нет, банк пустой». Проверять
`ls` по ОДНОМУ расширению нельзя — так и получается ложный вывод «лежит 4 файла
из 23». Смотреть все расширения сразу:

```bash
ls assets/audio/sfx/ | sed 's/\.[^.]*$//' | sort -u | wc -l   # сколько имён
ls assets/audio/sfx/*.wav 2>/dev/null                          # не забыть wav!
```

Скрипт заливки обязан отказываться писать `.ogg`, если рядом есть `.wav`:

```bash
check_shadowed() {   # $1 = целевой .ogg
	local base="${1%.ogg}"
	[ -f "$base.wav" ] && { echo "ПРОПУСК: есть $base.wav, .ogg мёртвый"; return 1; }
	return 0
}
```

Побочный эффект: после удаления лишних `.ogg` остаются **осиротевшие
`.import`** — Godot их сам не чистит. Проверка:

```bash
for f in assets/audio/sfx/*.import ; do [ -f "${f%.import}" ] || echo "сирота: $f" ; done
```

### 17.3 Сделать дефицит банка видимым

Пропавший звук игру не роняет — `play()` молча выходит. Поэтому список нужных
имён держать **константой**, а не «что нашлось», и отдавать отчёт:

```gdscript
const BANK_NAMES := ["shoot_pistol", ...]
const BANK_EXTS := [".wav", ".ogg", ".mp3"]

func missing() -> Array[String]:
	var out: Array[String] = []
	for n in BANK_NAMES:
		if not _bank.has(n):
			out.append(n)
	return out
```

Печатать `Audio.missing()` в отчёте headless-прогона. То же для музыки: файлы
`play_music()`/`play_ambience()` проверять через `ResourceLoader.exists()` —
**отсутствующая папка `assets/audio/music/` означает полную тишину по музыке и
амбиенту, и в логе об этом не будет ни строчки.**

### 17.4 Не забыть `--import`

Новые `.ogg`/`.wav` без `godot --headless --path <proj> --import` не получают
`.import`, и `ResourceLoader.exists()` вернёт **false** — банк снова пустой,
хотя файлы на месте. После заливки аудио `--import` обязателен.

## 18. Godot НЕ создаёт проект из пустой папки — нужен минимальный `project.godot`

Проверено на 4.7.2: на пустой папке **ни** `godot --path <dir> --editor --quit`,
**ни** `godot --path <dir> --import` не создают ничего. Обе команды молча
выходят с кодом 0, `project.godot` не появляется, `.godot/` тоже. То есть
«создать проект» из CLI нельзя — надо **сначала написать минимальный
`project.godot` руками**, и только потом Godot его подхватит и достроит.

Минимум, который Godot принимает и достраивает (проверено):

```ini
; Engine configuration file.
; config_version=5 — обязателен, иначе Godot скажет «unrecognized config_version»
config_version=5

[application]

config/name="test_0"
config/features=PackedStringArray("4.7", "Forward Plus")
```

`config/features` — массив `"<версия>", "<рендерер>"`; рендерер писать ровно как
в редакторе: `Forward Plus`, `Mobile` или `GL Compatibility`.

Дальше:

```bash
godot --headless --path <dir> --editor --quit
```

Это НЕ просто «открыть и закрыть»: движок создаёт `.godot/`, сканирует файловую
систему, собирает `.godot/global_script_class_cache.cfg` и перезаписывает
`project.godot` уже в полном виде (добавляет секции `[display]`, `[rendering]`
и т.д.). После этого папка — настоящий проект.

**Проверка успеха (обе обязательны):**

```bash
ls <dir>/project.godot          # есть
ls -d <dir>/.godot              # есть
```

Если `.godot/` нет — импорт не отработал (частые причины: `APPDATA` не
проброшена, см. §0; или в `project.godot` опечатка в `config_version`).

**Главная сцена задаётся отдельно.** `config/features` её не содержит; чтобы
проект стартовал с нужной сцены, дописать в `[application]`:

```ini
run/main_scene="res://Main.tscn"
```

Но безопаснее не писать в файл руками (редактор/движок может затереть, см.
§12.1), а сделать это через `ProjectSettings` из самого Godot — тогда значение
гарантированно то, которое движок прочитал:

```gdscript
var ps := ProjectSettings
ps.set_setting("application/run/main_scene", "res://Main.tscn")
ps.save()
```

**Идемпотентность.** Инструмент/скрипт создания проекта должен ПЕРВЫМ делом
проверять `project.godot`: если он есть — не трогать (иначе повторный вызов
перезапишет `config/name` и настройки, которые пользователь уже поменял).
Возвращать при этом `created: false`, а не ошибку.

**Порядок «пустая папка → работающая игра»:**

1. написать минимальный `project.godot` (см. выше);
2. `godot --headless --path <dir> --editor --quit` → появился `.godot/`;
3. строить сцены/скрипты (`.tscn` пишет сам Godot, не текст руками);
4. `godot --headless --path <dir> --import` — импорт новых ассетов;
5. назначить `run/main_scene` через `ProjectSettings.save()`;
6. `godot --headless --path <dir> --quit-after N` — прогон без окна, ловит ошибки;
7. обычный запуск (без `--headless`) — окно игры.

**Чего НЕ делать:** не пытаться «создать проект» через
`--editor --quit` на пустой папке (не работает), и не писать `.tscn`
текстом вручную (Godot молча игнорирует неизвестные секции → битый файл).
Сцены должны создавать либо редактор, либо инструмент, который генерирует
SceneTree-скрипт и прогоняет его через `--script`.
