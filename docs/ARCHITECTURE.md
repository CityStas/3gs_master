# 3GS_Master

Локальная среда для создания игр и сцен на **трёх движках**: Three.js (браузер),  
**Godot 4.7** и **Unity 6000.3**. У каждого - свой RAG по своей документации и свой  
профиль агента `pi`, но общая инфраструктура: одна модель, одни серверы, один `.venv`,  
один пайплайн ассетов.

Всё считается на машине. Облако (DeepSeek, workbuddy и т. п.) - опция, а не требование.

> **Перед генерацией ассетов прочитать [`ASSET-POLICY.md`](ASSET-POLICY.md).**  
> Коротко: своя генерация в первую очередь для персонажей, врагов, оружия, ключевого  
> арта и сцен; интернет-ассеты - второй эшелон для тайлов, звука, шрифтов и заглушек;  
> облачные генераторы не используются. Правила целиком — в `AGENTS.md` в корне.
>
> **Unity-стек описан отдельно — [`unity/README.md`](../unity/README.md)**, правила агента  
> для Unity-проектов — [`unity/AGENTS.md`](../unity/AGENTS.md). Ниже в этом файле — то,  
> что общее для всех трёх движков, и краткая карта Unity-слоя.

```
        запрос
          │
          ▼
   ┌─────────────┐    ┌──────────────┐    ┌───────────────┐
   │ pi-агент    │───▶│ RAG (SQLite) │    │ z-image-turbo │
   │ Qwen3.5-9B  │    │ docs+source  │    │ sd-server     │
   │  :8080      │───▶│ :8081 embed  │───▶│ :8687  (~20с) │
   │             │    │ :8083 rerank │    │               │
   └─────────────┘    └──────────────┘    └───────────────┘
          │                                      │
          │              ┌───────────────┐       │
          └─────────────▶│ ComfyUI :8188 │◀──────┘
                         │ надписи / маски│  (не сосуществуют:
                         │ / 3D high     │   одна карта)
                         └───────────────┘
                                 │
           projects/games/ ◄─────┘
                assets/{images,masks,3d,splats}   (Three, Godot)
                Assets/Generated/                 (Unity)
```

Один и тот же `:8080` обслуживает все три движка: профиль агента выбирается по  
`engine.json` проекта, а модель одна. Держать три LLM одновременно не нужно и негде -
на 8 ГБ VRAM живёт ровно одна.

## Быстрый старт

Все команды - из корня проекта. Открой `cmd.exe`, **перейди в каталог** и запускай:

```cmd
cd /d F:\Pets\Projects\local_tools\3GS_Master
```

> `cmd.exe` не ищет программы в текущем каталоге: запуск `serve-all.cmd` из чужого
> места (`C:\Users\...`) даёт «не является внутренней или внешней командой». Поэтому
> сначала `cd`, и только потом команда. В PowerShell те же имена требуют префикса `.\`
> (`.\gs.cmd up`).

Приглашение должно выглядеть так:

```
F:\Pets\Projects\local_tools\3GS_Master>
```

### 0. Основной способ: агент `pi` в консоли

```cmd
dev.cmd test
```

Одна строка делает всё: поднимает обе модели в отдельных окнах, **дожидается,  
пока они реально ответят**, проверяет окружение и открывает сессию агента на  
нужном проекте. Аргумент — **имя игры** в `projects\games\` (не путь).

Хочешь видеть результат рядом — добавь `--studio`, и студия откроется в  
**параллельном** окне:

```cmd
dev.cmd test --studio
```

Студия — только просмотр и ручная правка; агента в ней нет. Она запускается  
независимо и закрывается, не трогая сессию `pi`: они делят лишь файлы на диске.

**Ничего не создаётся, кроме самой папки.** `dev.cmd <имя>` заводит пустой  
`projects\games\<имя>\` и сразу передаёт его агенту: ни `scene.js`, ни `level.json`,  
ни `tools\`, ни `serve.py` там не появятся. Модель раскладывает то, что ей нужно,  
сама — пустая папка это нормальный старт, а не ошибка.  

Стандартный стек кладёт **только явный** `newgame.cmd <имя>` (а `--cli` — его  
урезанный слой без студии). Раньше отсутствие `web3d\levels.json` молча тянуло за  
собой `newgame.cmd`: одна строка «запусти агента» переписывала дерево файлов. Флаги  
`--force` и `--cli` у `dev.cmd` убраны — они делали ровно это, и теперь отбиваются  
сообщением `no longer a dev.cmd flag` (rc=2).

То же вручную, если нужна цепочка по шагам:

```cmd
serve-all.cmd && cmd\doctor.cmd && agent.cmd projects\games\test
```

`cmd\doctor.cmd` в цепочке не украшение: он даёт код возврата 1 при проваленной  
проверке, и `&&` честно останавливает цепочку **до** запуска агента. `agent.cmd`  
прогоняет ту же проверку сам, так что отдельный вызов — это подстраховка, а не  
обязательное звено.

Всё остальное — про этот способ: §1–§4 ниже и «Работа с агентом».

### 0.1 Студия (необязательно, работает параллельно)

Студия — инструмент живого просмотра и ручной правки: редактор уровня 2D/3D,
превью картинок, GLB-просмотрщик. **Агента в ней нет** — модель работает только
через консольный `pi` (`agent.cmd`).

```cmd
studio.cmd
```

Сервер игры и браузер поднимаются вместе, `Ctrl+C` в том же окне гасит всё.
Это **не замена** консольному агенту и не его часть: студия запускается
параллельно, в любой момент, независимо. Смысл связки — агент правит
`level*.json` в консоли, а студия показывает результат (открой или перезагрузи
страницу) и даёт поправить это мышью. Модели она поднимает лишь потому, что их
использует консольный агент, — самой студии они не нужны (`--no-models`).

### 0.2 Единая точка входа: `gs.cmd`

Запоминать с десяток имён не нужно — `gs.cmd` в корне раздаёт их по подкомандам:

```cmd
gs up                       :: serve-all.cmd - поднять обе модели и дождаться готовности
gs dev my_game              :: модели + doctor + агент одной командой
gs dev my_game --studio     :: то же + студия в параллельном окне
gs agent projects\games\my_game      :: интерактивная сессия pi
gs ask "включи тени от directional light"   :: разовый запрос без сессии
gs resume projects\games\my_game     :: продолжить прошлую сессию
gs studio my_game           :: студия одним окном
gs newgame my_game          :: скелет новой игры
gs gen -p my_game -j plan.json
gs check my_game            :: tsc-гейт
gs img "изумрудный кристалл" assets\images\crystal.png
gs index | gs doctor | gs test | gs log --last
gs llm | gs embed | gs vlm  :: поднять один сервер напрямую
```

`gs` — только фасад: он вызывает те же скрипты, что и раньше, и пробрасывает им  
аргументы как есть (код возврата — как у вызванного скрипта). Прямые вызовы  
`serve-all.cmd`, `agent.cmd`, `studio.cmd`, `resume.cmd` из корня работают как и  
прежде — их не трогали. Остальные лаунчеры переехали в `cmd\` (например,  
`cmd\doctor.cmd`), но доступны и напрямую, и через `gs`.

### 1. Поднять модели (три окна консоли)

```cmd
serve-all.cmd
```

Откроются три окна: `3gs-llm` (:8080), `3gs-embed` (:8081) и `3gs-rerank` (:8083).  
**`serve-all.cmd` не возвращает управление, пока не ответят оба ОБЯЗАТЕЛЬНЫХ сервера**  
(LLM и embedding) - 9B грузится ~30 с с холодного диска и ~8 с из кэша страниц. Прогресс  
печатается в текущее окно:

```
Waiting for the servers to finish loading (9B needs about 30 s)...
  [ ready ] EMBED http://127.0.0.1:8081/health  (2.1s)
  [ ready ] LLM   http://127.0.0.1:8080/v1/models  (8.1s)
servers ready in 8.1s
  [ ready ] RERANK http://127.0.0.1:8083/health
```

Реранкер ждать **не нужно и нельзя**: он ускоряет и уточняет поиск, но не является  
зависимостью. Если он не поднялся, поиск работает на гибридной паре и учитывает сбой в  
`rerank_failures` - поэтому `wait_ready.py` его не требует, а `serve-all.cmd` просто  
запускает отдельным окном, когда порт свободен.

Нужно вернуть управление сразу (серверы поднимутся сами) - `serve-all.cmd --no-wait`.  
Если обязательные порты не ответили за 300 с, скрипт печатает `TIMEOUT` и выходит с кодом 1.

Проверить, не глядя в окна:

```cmd
curl http://127.0.0.1:8080/health
curl http://127.0.0.1:8081/health
curl http://127.0.0.1:8083/health
```

Ожидаемый ответ всех трёх - `{"status":"ok"}`.

### 2. Проверить окружение

```cmd
cmd\doctor.cmd
```

Печатает таблицу: venv, LLM, embedding, каталоги корпуса, индекс, ComfyUI.  
Каждая строка - `ok`, `warn` или `FAIL` с причиной. **Код выхода 1, если хоть одна  
обязательная проверка провалилась** - поэтому `cmd\doctor.cmd` нельзя ставить в цепочку  
через `&&` раньше, чем серверы готовы (см. «Запуск одной строкой»).

### 4. Работать с агентом

```cmd
agent.cmd C:\path\to\your\threejs-project
```

Интерактивная сессия. Проект запоминается в `data\active_project.txt` - дальше можно  
запускать без аргумента. `agent.cmd` сам прогоняет `doctor.py` перед стартом, так что  
отдельный `cmd\doctor.cmd` **не обязателен**. В цепочке `serve-all.cmd && cmd\doctor.cmd &&
agent.cmd` он всё равно полезен: проверка идёт отдельным шагом и, если что-то  
провалено, `&&` останавливает цепочку до запуска агента — вы это видите, а не  
разбираетесь потом, почему агент отвечает странно.

**Какая игра активна — вписывается в системный промпт.** Рабочий каталог pi всегда
корень репозитория, и `pi` не читает `THREE_PROJECT` сам. Поэтому `agent.cmd` передаёт
игру через `pi --append-system-prompt`: `Active game: projects\games\<имя> (working dir stays the
repo root…)`. Без этого модель знает только `<cwd>` = корень, угадывает папку по
формулировке задачи («демо» → `projects\games\demo`) и выдумывает файлы. Больше в системный
промпт не дописывается **ничего**: ни имени брифа, ни имени файла задачи — сообщение,
с которым запущен агент, и есть задача. Проверить, что модель видит игру: строка
`project : projects\games\<имя>` в шапке запуска, а `data\active_project.txt` всегда
синхронизируется.

**Путь у указателя ОДИН на все стеки: `<репозиторий>\data\active_project.txt`.** Это не
файл стека: пишет его `agent.cmd`, читают threejs, godot, unity (через `resolve_project`)
и `.pi/extensions/engine-gate.ts` — последний выбирает движок сессии. У godot и unity свои
`data\active_project.txt` остались только как legacy-фолбэк (читаются вторым).

**Указатель — подсказка, а не факт.** `projects\games\` — данные пользователя: игры
создаются, переименовываются и удаляются, а указатель продолжает называть старую. Поэтому
он разрешается на КАЖДОМ вызове (не кэшируется на импорте), а мёртвый указатель даёт ошибку
с именем мёртвого пути: Python бросает `ValueError`, `engine-gate` пишет `STALE` в stderr.
Молчаливый фолбэк на `threejs` — худший исход: агенту выдали бы не ту поверхность
инструментов, и в логах не было бы ничего. `is_dir()`, а не `exists()`: файл с именем
проекта не должен его подменять.

**Лаунчер проверяет указатель до записи.** `agent.cmd` без аргумента читает указатель и
пишет его обратно, поэтому мёртвый указатель жил бы вечно — перезапуск его воскрешал.
Проверка вынесена в `tools\active_project.py` (тот же `resolve_project`, а не второй набор
правил в batch): при мёртвом указателе печатается путь, файл очищается и агент идёт веткой
«проекта нет». Проверяется **только указатель** — явный аргумент это дело вызывающего, и
он же лечит файл, перезаписывая его ниже.

Разовый запрос без интерактива:

```cmd
cmd\ask.cmd "добавь в сцену OrbitControls и тени от directional light"
```

**Приложить бриф из файла.** Всё, что идёт после пути к проекту, `agent.cmd` передаёт
в pi как есть. Текстовый файл подключается аргументом `@path` — это аргумент
командной строки, а **не** синтаксис внутри сообщения (`@file` в тексте сообщения
останется просто текстом):

```cmd
agent.cmd projects\games\my_game "@projects\games\my_game\<ваш файл>.md"
```

`@path` резолвится от текущего каталога, то есть от корня `3GS_Master`.

**Имени брифа по умолчанию нет.** `agent.cmd` ничего не ищет и не подсказывает:
бриф — это файл, который вы назвали сами, и только если он вам нужен. Без него
задача — это сообщение, с которым запущен агент.

### Запуск одной строкой

Короткий вариант — весь цикл одним лаунчером (`--studio` добавляет студию рядом):

```cmd
cd /d F:\Pets\Projects\local_tools\3GS_Master && dev.cmd my_game --studio
```

Полный ручной вариант — с проверкой окружения:

```cmd
cd /d F:\Pets\Projects\local_tools\3GS_Master && serve-all.cmd && cmd\doctor.cmd && agent.cmd projects\games\my_game
```

`serve-all.cmd` блокирующий, поэтому `&&` здесь безопасен. А вот `cmd\doctor.cmd` в  
середине цепочки ломал запуск: `start` в старом `serve-all.cmd` возвращал управление  
мгновенно, `doctor` проверял LLM через 3 с (модель ещё грузилась), получал код 1, и  
`cmd` молча пропускал всё после `&&` - включая `agent.cmd`.

**Про `GDM_ENABLE_ASSET_TOOLS=1`.** Этой переменной в репозитории больше нет:  
она осталась от прежнего GDM-агента (Godot) и сейчас ничего не включает. Ставить  
её в цепочку бессмысленно. Инструменты ассетов доступны всегда — `cmd\gen.cmd`  
(`tools/generate.py`) не проверяет окружение, а правила работы с ассетами лежат  
в `ASSET-POLICY.md`.

### «`serve-all.cmd` перестал открывать окна»

Это не поломка. Скрипт **намеренно** не спавнит вторую пару, если оба порта уже  
отвечают: два новых окна умерли бы на занятом порту, а старые инстансы продолжили  
бы отвечать — то есть выглядело бы как успех при живом старом процессе.

Так бывает, когда окна закрыли, а `llama-server` пережил закрытие консоли и остался  
висеть на порту. Проверить и увидеть, кто держит порт:

```cmd
.venv\Scripts\python.exe tools\wait_ready.py --status
```

```
local servers:
  LLM    :8080  up    pid 8868
  EMBED  :8081  up    pid 7284
  RERANK :8083  up    pid 7310 (optional)
```

Реранкер помечен `(optional)`: его отсутствие печатается как `DOWN`, но **не влияет на  
код возврата** - иначе упавший реранкер краснил бы `serve-all.cmd --check` и скрипт  
открывал бы вторую пару окон поверх живой.

Перезапустить честно — одной командой:

```cmd
serve-all.cmd --restart
```

Она снимает то, что слушает :8080/:8081/:8083 (`wait_ready.py --stop`, только эти три  
порта), и поднимает серверы заново. Остановить, не поднимая:

```cmd
.venv\Scripts\python.exe tools\wait_ready.py --stop
```

### Продолжить прошлую сессию

`resume.cmd` добавляет `--continue` и пробрасывает остальные аргументы так же, как  
`agent.cmd`. pi продолжает **тот же** файл сессии, а не начинает новый:

```cmd
resume.cmd projects\games\my_game
resume.cmd projects\games\my_game "@projects\games\my_game\continue.md"
```

Второй вариант - обычный способ передать эстафету: `continue.md` ложится в контекст  
как вложенный файл, и модель видит, на чём именно оборвалась прошлая попытка.

**Если сессию запускает агент (а не вы руками).** Из-под агентской оболочки `cmd //c`  
до лаунчера не доходит: при снятой песочнице вызов отбивается («Invoking cmd.exe from  
Bash bypasses all command validation»), под песочницей получает SIGTERM. Единственный  
рабочий путь - задача Планировщика, она живёт вне дерева процессов агента:

```cmd
schtasks /query /tn 3gs-resume-agent
```

Задача зарегистрирована как `cmd.exe /k "cd /d <repo> && serve-all.cmd && resume.cmd
projects\games\my_game @projects\games\my_game\continue.md continue"` с `RunLevel Limited` и  
без лимита времени. Запуск и остановка - через `Start-ScheduledTask` / `Stop-ScheduledTask`  
или `schtasks`. Удалить, если не нужна: `schtasks /delete /tn 3gs-resume-agent /f`.

### 5. Тесты (после правок кода)

```cmd
cmd\test.cmd
```

Ожидаемый итог - `ALL TEST FILES PASSED`. Файлов семь: `test_smoke` (RAG + ассеты,  
Three.js), `test_scheduler`, `test_asset_paths` (16, герметичные - не ходят в живую игру),  
`test_project_paths` (11), `test_pagecheck`, `test_unity` (стек Unity) и `test_rag_parity` -  
**кросс-стековые**: каждый тест прогоняется по всем трём деревьям (`threejs/`,  
`godot/gdmaster/`, `unity/unimaster/`) и падает с именем стека, если контракт выполнен не  
везде. Именно они ловят фикс, применённый к одному дереву и забытый в двух других.

`test_project_paths` держит контракт указателя активного проекта: живой указатель  
разрешается, мёртвый (относительный и абсолютный) даёт `ValueError`, голое имя уходит под  
`GAMES_DIR`, `GAMES_DIR` не приклеивается дважды, явный абсолютный аргумент не трогается,  
и - отдельной проверкой - **все три стека читают ОДИН файл**. Логика `engine-gate.ts`  
проверена разовым пробником, в набор не входит: набор Python-only.

Новый файл в `tests/` обязан быть добавлен в список `for %%F in (...)` в `cmd\test.cmd` -  
иначе он просто не запускается, и «все тесты прошли» становится неправдой.

### 6. Проверка типов игры

```cmd
cmd\check.cmd my_game
```

`cmd\check.cmd` компилирует проект локальным `tsc` (не `npx` - тот может решить, что пакет

не установлен, и задать вопрос, а TTY нет) и печатает компактный отчёт: вердикт, счётчик  
ошибок по файлам, все содержательные ошибки целиком и неиспользуемые символы одной  
строкой каждый. Сырой `tsc --noEmit` - это 50+ строк, а `| head -50` прячет все файлы  
после пятидесятого, из-за чего ошибки правятся по одной и общая картина теряется.

```cmd
cmd\check.cmd my_game --full      :: сырой вывод tsc
```

## Студия: уровень 2D/3D + ассеты + GLB

Одна страница вместо трёх окон: уровень (правка мышью, слои, инспектор), превью

`python -m http.server`: панели ассетов, сохранение правок и пересборка — это его ручки.

Запуск — один файл, одно окно (можно дважды щёлкнуть в проводнике):

Официальный сервер `@modelcontextprotocol/server-threejs` (репозиторий

материал, не поднимая dev-сервер игры.

### `threejs-devtools` - инспекция ЖИВОЙ сцены

`threejs-devtools-mcp` (v0.4.1, 59 инструментов): дерево сцены, материалы, шейдеры,  
текстуры, анимации, перф, утечки, скриншоты, модификация на лету, `gltf_to_r3f`.

Требует запущенный dev-сервер игры и **сам поднимает Chrome** через `puppeteer-core`.  
Связь идёт по WebSocket, так что закрытая вкладка = инструменты не работают.

#### Почему он спамит вкладкой «Waiting for Server»

Разобрано по исходнику `dist/index.js`:

```js
var preferredPort = Number(process.env.BRIDGE_PORT) || 9222;
var port = await findFreePort(preferredPort);
var devTarget = process.env.DEV_URL ? process.env.DEV_URL
              : process.env.DEV_PORT ? Number(process.env.DEV_PORT) : await detectDevPort();
var bridge = new BridgeServer(port, devTarget);
bridge.onReady(async () => {
  browserResult = await launchBrowser(`http://localhost:${port}`, {
    headless: process.env.HEADLESS === "true"
  });
});
```

Три следствия:

1. **Браузер открывается безусловно, на каждом старте сервера.** `headless` по умолчанию  
   `false`, то есть это видимое окно Chrome. Флага «не открывать» нет - `HEADLESS` только  
   меняет режим на невидимый.
2. **Порт моста случайный** - `findFreePort(9222)`, и если 9222 занят, уходит далеко  
   (в наблюдении - 54631). `BRIDGE_PORT` пинит его.
3. **Целевой dev-порт угадывается** (`detectDevPort()` читает `package.json`), и при неудаче  
   это `3000`. Если игра на другом порту - страница вечно ждёт сервер и автообновляется.

Плюс WorkBuddy запускает **по экземпляру на сессию и на prewarm-воркер** - наблюдалось три  
одновременно. Кнопка «Trust» в панели коннекторов **снимает `disabled`** и перезаписывает  
`mcp.json`, поэтому флаг `disabled: true` тут не защита: выключение делается тумблером в  
панели коннекторов, а не правкой файла.

#### Безопасная конфигурация, если он нужен

```json
"threejs-devtools": {
  "command": "npx",
  "args": ["-y", "--silent", "--registry=https://registry.npmjs.org/", "threejs-devtools-mcp"],
  "env": { "HEADLESS": "true", "DEV_PORT": "5173" },
  "disabled": true
}
```

`HEADLESS=true` - Chrome невидимый (бинарник найден в `C:\Program Files\Google\Chrome`),  
`DEV_PORT` - реальный порт dev-сервера игры, иначе страница ждёт `:3000` впустую.

Включать точечно, когда нужна именно живая сцена, и выключать обратно: 59 схем инструментов

- заметная доля контекстного окна, для локальной 9B-модели агента такой выбор перебор.

### Чего сознательно НЕ подключено

`three.ws` - реальный провайдер с 361 инструментом (в т.ч. `look_at_model`: рендерит GLB  
с нескольких ракурсов и отдаёт кадры картинками, плюс разбор геометрии). Не подключён по  
двум причинам:

1. `ASSET-POLICY.md` запрещает hosted-генераторы - а у них `forge_free`, `text_to_3d`,  
   `image_to_3d` именно такие (часть платные, в USDC по x402).
2. Даже бесплатный `look_at_model` требует **публично доступный URL** до GLB, а ассеты  
   проекта лежат локально в `public/assets/`.

Если понадобится - бесплатный 3D-стенд (`/api/mcp-studio`, транспорт remote, без auth)  
даёт `look_at_model`, `preview_3d`, `inspect_model`, `remesh_model` без платежей.

## Unity-стек (`unity/`)

Третий движок добавлен как **равноправный**, а не как приложение к Three.js: свой корпус,  
свой RAG, свой профиль агента, свой набор инструментов. Общее - только серверы и `.venv`.

```
unity/
├─ unimaster/            код: RAG (rag/), Unity-слой (unity/), MCP (mcp/)
├─ tools/                fetch_docs.py, index.py, doctor.py, check.py
├─ knowledge/            корпус: official_docs, official_source, packages_docs,
│                        cookbook, recipes, troubleshooting, anti_patterns
├─ data/                 индекс (своя SQLite), логи. Указатель активного проекта - ОБЩИЙ,
│                        `<репозиторий>\data\active_project.txt` (см. «Работать с агентом»)
├─ pi-home-unity/        ИЗОЛИРОВАННЫЙ agent-dir pi для Unity (SYSTEM.md + 7 скиллов)
├─ AGENTS.md             правила работы в Unity-проекте (справочник для человека)
└─ README.md             полная документация стека
```

**Профиль выбирается по `engine.json`.** `agent.cmd` читает `engine` из активного проекта  
и подставляет `PI_CODING_AGENT_DIR`:

| `engine`          | Профиль           | MCP-серверы у модели                       |
| ----------------- | ----------------- | ------------------------------------------ |
| `godot`           | `pi-home-godot`   | `godot`, `assets`                          |
| `unity`           | `pi-home-unity`   | `unity-rag`, `unity-project`, `assets`     |
| `threejs` / нет   | `pi-home-three`   | `threejs-rag`, `assets` (+ студия)         |

Инструменты регистрирует не промпт, а расширение `.pi/extensions/engine-gate.ts`:  
под Unity-профилем модель **не видит** godot-инструментов вообще, потому что они не  
зарегистрированы. 9B-модель не может вызвать инструмент, которого нет в `tools/list` -  
это надёжнее любого запрета в тексте.

**`engine-gate.ts` проверяет указатель, а не доверяет ему.** Он читает
`<репозиторий>\data\active_project.txt` и `engine.json` внутри проекта. Раньше
существование пути не проверялось: удалённый проект давал `readEngine() == null`, движок
молча становился `threejs`, и агенту выдавалась не та поверхность инструментов — без
единой строки в stderr. Теперь мёртвый указатель (в том числе указывающий на ФАЙЛ, а не
каталог) печатает `[engine-gate] the active project is STALE: …` и **не регистрирует
серверы ни одного движка**. Указателя нет вовсе — это по-прежнему нормальная сессия
three.js, и она молчит.

> **У UPM-пакетов TOC устроен иначе**, и это выяснено пробами, а не догадкой: `toc.json` там
> **404**, список страниц лежит в `<sec>/toc.html` обычными `<a href>`, а алиаса `@latest`
> **не существует** — нужна конкретная версия. Поэтому версия берётся из реестра Unity
> (`https://packages.unity.com/<name>` → `dist-tags.latest`) и обрезается до `major.minor`
> (сайт документирует `@1.20`, а `1.20.1` даёт 404).

Исходник важнее отрендеренной страницы: в `UnityCsReference` лежат настоящие атрибуты,  
дефолты и перегрузки **установленной** версии, а страница API их часто опускает.

> **`Modules/` в исходнике обязателен.** В репозитории 5774 `.cs`: `Modules/` - 3712,
> `Editor/` - 1497, `Runtime/` - 515. Всё, что агент реально вызывает (`Rigidbody`,
> `Transform`, `NavMeshAgent`, `Animator`), лежит в `Modules/`. Первый вариант фетчера брал
> только `Runtime/` + `Editor/` - и в корпусе не оказалось ни физики, ни анимации, ни
> навигации. Состав корпуса надо проверять по реальному дереву репозитория, а не по памяти
> о его структуре.

> `docs.unity3d.com` жёстко режет частоту: залп из 8 воркеров получил **2225 отказов HTTP 429  
> из 2827** страниц Manual. Поэтому фетчер ходит по 4 и на 429/5xx ждёт с экспоненциальной  
> задержкой (уважая `Retry-After`), а не бросает страницу. Файлы докачиваются идемпотентно -  
> повторный запуск берёт только отсутствующие.

### Два правила, которые закрывают типовые провалы

**Сцены и префабы не пишутся текстом.** `.unity`/`.prefab` - это YAML с GUID-ссылками на  
`m_Script` и локальными id. Написанный руками файл синтаксически валиден и мёртв: сцена  
открывается, компоненты пустые, **исключения нет**. Правильный путь - editor-скрипт,  
который исполняет сама Unity (`unity_run_method` → `-batchmode -executeMethod`), и тогда  
YAML пишет движок. Это ровно та же логика, что «сцена Godot меняется через `SceneTree`-скрипт,  
а не правкой `.tscn`».

**Линт Unity 5/6 API - отдельный слой.** Компилятор проверяет синтаксис, а не существование  
API. `rb.velocity`, `transform.rigidbody`, `Application.LoadLevel`, `WWW`, `FindObjectsOfType<T>()`  
пишутся моделью по памяти (в обучающих данных на порядок больше Unity 5) и либо не компилируются,  
либо тихо ломаются в рантайме. `unity_validate` дописывает находки в `warnings` и разделяет их  
по severity: `error` краснит вердикт, `warning` - нет (`NavMeshAgent.velocity` существует,  
поэтому `.velocity` сам по себе - только предупреждение).

Отдельный кейс - **Input System**. Если в `ProjectSettings.asset` стоит  
`activeInputHandler: 1` («Input System Package (New)» only), то любой `UnityEngine.Input.*`  
бросает `InvalidOperationException` в рантайме. Линт видит это по проекту и делает ошибкой.

### Проверка без агента

```cmd
gs unity-fetch                 :: докачать корпус (идемпотентно)
gs unity-index                 :: собрать индекс
gs unity-check my_unity_game   :: линт; --compile добавляет компиляцию редактором
gs unity-doctor                :: редактор, корпус, индекс, серверы
```

`unity-check` - аналог `check.cmd` для Three.js, и по той же причине: дешёвый слой  
(линт, секунды) ловит то, что видно без движка, дорогой (`--compile`, минуты) - то, что  
видит только движок. Вердикт по худшему, код возврата 1 при ошибках.

> **Один редактор на проект.** Unity отказывается открывать уже открытый проект: batch-прогон  
> против живого редактора падает не с ошибкой компиляции, а с локом. `unity_validate(compile=true)`  
> проверяет `Temp/UnityLockfile` **до** запуска и говорит об этом прямо.

## Генерация ассетов

Движок - ComfyUI как sidecar на `:8188`. Поднимает и опускает его **планировщик**, а не  
первый вызов инструмента: см. «Сериализация» ниже.

### Сериализация: один GPU - одна модель

На этой машине 8 ГБ VRAM и два процесса, каждому из которых нужно всё:

| Кто               | Сколько просит                      |
| ----------------- | ----------------------------------- |
| `llama-server` 9B | ~6.4 ГиБ VRAM + ~6.4 ГБ RAM         |
| Qwen-Image 2.1    | ~8.9 ГиБ text encoder (`--lowvram`) |

Вместе они не влезают. Замер: при живом 9B картинка 512×512 в 4 шага заняла **725 с**,  
`QwenImage21TEModel_` стейджил 8916 МБ, свободной VRAM оставалось 426 МиБ - карта  
выгружала 9B в системную память на каждом шаге денойза.

Поэтому генерация сериализована по построению. Агент сначала решает, что игре нужно,  
и отдаёт **весь список одним вызовом** `asset_generate_pack`. Дальше:

```
1. план        агент пишет список задач (картинки, 3D, пути)
2. llm off     :8080 убит; освобождение VRAM проверено через nvidia-smi
3. comfy up    одна сессия ComfyUI на весь пакет
4. генерация   все задачи подряд в data/gen-staging/<run>/
5. comfy off   карта возвращается
6. размещение  файлы переезжают в проект по своим финальным путям
7. llm on      :8080 поднят, агент продолжает с готовыми файлами
```

На шагах 3-5 языковая модель **выключена** и не потребляет ничего. Шесть ассетов в  
пакете - это один старт ComfyUI и одна перезагрузка 9B; шесть отдельных вызовов  
заплатили бы за это шесть раз.

Пакет переживает сбой отдельной задачи: остальные всё равно выполняются, а зависевшие  
от упавшей пропускаются с причиной. 9B возвращается из `finally` - даже если упало всё,  
агент остаётся дееспособным.

Готовые файлы кладутся туда, куда сказал агент (`out` в задаче), а без `out` - в  
`public/assets/<images|masks|3d>/<имя>.<ext>`. В ответе на каждый файл есть `rel`  
(путь от корня проекта) и `url` (`/...`, если файл под `public/` - то есть готовый  
путь для рантайма).

Проверить, кто держит карту:

```cmd
cmd\gen.cmd --status
```

```
3GS_Master - GPU arbitration
  invariant  : at most one of llama-server :8080 and ComfyUI :8188 is resident
  llm  :8080 : UP  pid 3428
  comfy:8188 : down
  vram   : 7095 MiB used / 912 MiB free of 8192 MiB
  lock       : free
```

Если оба `UP` - кто-то поднял ComfyUI в обход планировщика, и генерация будет  
медленной.

### Запуск пакета из консоли

`cmd\gen.cmd` - тот же планировщик, что и у агента. План - JSON-файл  
(образец со всеми полями: `assets\pack.example.json`):

```cmd

cmd\gen.cmd -p my_game -j plan.json --json     # сырой отчёт
```

Ручной запуск и запуск агентом берут один и тот же лок, поэтому наложиться не могут.

### Тиры качества 3D

| Тир       | Workflow            | Время        | Что даёт                                                           |
| --------- | ------------------- | ------------ | ------------------------------------------------------------------ |
| `high`    | Pixal3D / TRELLIS.2 | ~16-18 мин   | Настоящий mesh с UV-развёрткой и PBR-текстурами. **По умолчанию**  |
| `economy` | TripoSplat          | ~2.5-3.5 мин | Gaussian splat + vertex-colour mesh. Без UV, `KHR_materials_unlit` |

`high` - для всего, что стоит в сцене со светом; `economy` игнорирует освещение и  
годится только для превью и одноразовых пропов.

#### Скорость и размер: `faces_3d` и `steps_3d`, а не `resolution_3d`

Замер на одном концепте (`quality: "high"`):

| `resolution_3d` | время    | GLB     | граней  |
| --------------- | -------- | ------- | ------- |
| 512             | 1051.6 с | 40.2 МБ | 698 448 |
| 1024            | 955.7 с  | 42.1 МБ | 698 818 |

Разницы нет - 1024 вышел даже быстрее (первый прогон платил за холодную  
загрузку весов). `resolution_3d` едет в `312 ImageCropToMask`, то есть меняет  
размер **входной картинки**, а TRELLIS.2 всё равно приводит её к своему  
внутреннему размеру.

Что действительно работает:

- **`faces_3d`** - сколько граней оставить после `186 DecimateMesh`. В воркфлоу  
  стоит `target_face_count: 700000`, отсюда ~40 МБ на проп. Для 2D-игры, где  
  спрайт занимает ~15 % высоты кадра, ставить **5 000-20 000**.
- **`steps_3d`** - суммарно 56 шагов на четыре сэмплера (узлы 3/12/18/23:  
  12/12/20/12). Время почти линейно: shape ~35-38 с/ит, texture ~18 с/ит.

## Standalone-движки

Живут в `bin/`, веса - в `models/`. Доступны и вручную, и из пайплайна.

### z-image-turbo (текст → картинка) — движок по умолчанию

`bin/sd-vulkan/sd-server.exe` - stable-diffusion.cpp на Vulkan, HTTP `:8687`.  
**Это основной генератор ассетов**, а не альтернатива: ~20 с на кадр 768×768,  
~45 с на слой 1856×768, 3.8 ГБ VRAM (текстовый энкодер Qwen3-4B работает на CPU).  
ComfyUI с Qwen-Image 2.1 остаётся подстраховкой для читаемых надписей, точной  
перекраски, вырезания фона и 3D.

```bash
# из пака (обычный путь)
tools/generate.py -p projects/games/<name> -j <plan.json>     # kind: image → z-image по умолчанию

# одиночный кадр вручную, без сервера
cmd\sd-image.cmd "изумрудный кристалл на тёмном камне" assets\images\crystal.png 8 1024 1024
```

Тюнинг: 8 шагов, `euler` / `sgm_uniform`, `cfg 1.0`, `guidance 3.5`.  
`--vae-tiling` обязателен (без него VAE-декод на 768 px падает по OOM), `te=cpu`  
намеренно, `cache-dit` на Vulkan вреден. Подробности и замеры - `ASSET-POLICY.md`.

Веса: `models/image/z-image-turbo/` - `z_image_turbo-Q4_K.gguf` (3.86 ГБ),  
`Qwen3-4B-Instruct-2507-Q4_K_M.gguf` (2.50 ГБ), `ae.safetensors` (168 МБ).

### bge-reranker-v2-m3 (переранжирование)

`bin/llama/llama-server.exe` в режиме `--rerank --pooling rank`, эндпоинт  
`http://127.0.0.1:8083/v1/rerank`. Модель: `models/bge-reranker-v2-m3-Q8_0.gguf` (0.6 ГБ).

```cmd
gs rerank          :: или cmd\serve-rerank.cmd
```

**Порт именно 8083.** `:8082` занят сервером зрения Qwen2.5-VL (`cmd\vlm.cmd`) - два  
`llama-server` на одном порту подерутся, и один молча не стартует.

**Зачем отдельный сервер.** Гибридный поиск складывает два *независимых* числа: косинус  
между эмбеддингами и BM25 между запросом и чанком. Ни одно из них не читает запрос и  
пассаж *вместе*, поэтому чанк, который просто повторяет слова запроса, может обойти  
пассаж, который на него отвечает. Кросс-энкодер читает пару совместно и судит это  
заметно лучше, поэтому работает вторым проходом по короткому списку (`RERANK_TOP_K=50`).  
Замер на корпусе Unity: настоящий ответ стоял на **46-м** месте лексики, реранкер поднял  
его на **5-е**.

**Результат - сырые логиты**, не вероятности: неограниченные и часто отрицательные.  
Смысл имеет только их порядок - сортировать по ним, никогда не сравнивать с порогом.

**Опционален.** Любой сбой даёт `RerankError`, ретривер возвращается к порядку RRF и  
увеличивает `rerank_failures`; `last_rerank_error` показывает причину. Мёртвый реранкер  
стоит релевантности, но не ответа. Отключить совсем - `THREE_RERANK_ENABLED=0` (или  
`GDM_`/`UNIM_RERANK_ENABLED`), либо `Reranker(...)` не передавать.

**Контекст.** `-c 8192 -np 4` = 2048 токенов на слот. Документ длиннее слота заставляет  
сервер ответить HTTP 400, поэтому клиент обрезает вход до `RERANK_MAX_CHARS=2000`.  
Меняешь `-c`/`-np` - пересчитай обрезку.

## Контекстное бюджетирование

Три числа обязаны совпадать, иначе компакция срабатывает не там:

| Где                     | Параметр                   | Значение |
| ----------------------- | -------------------------- | -------- |
| `cmd\serve-llm.cmd`         | `-c`                       | `65536`  |
| `pi-home/models.json`   | `contextWindow`            | `65536`  |
| `pi-home/settings.json` | `compaction.reserveTokens` | `16384`  |

pi считает порог компакции как `contextWindow - reserveTokens` и **не спрашивает  
сервер**. Поменять `-c` без `contextWindow` бесполезно. `reserveTokens` заодно  
ограничивает длину сводки (`maxTokens = 0.8 * reserveTokens`) - понижать нельзя.

KV-кэш Qwen3.5-9B стоит 17 КиБ/токен (гибридная архитектура: полный attention только  
в 8 блоках из 33). На 65536 это 1088 МиБ, всего ~6.4 ГиБ VRAM, ~1 ГиБ остаётся браузеру.

**Проектные настройки перекрывают агентские.** `pi` мержит `<cwd>/.pi/settings.json`  
поверх `pi-home/settings.json`. Поэтому `.pi/settings.json` держим пустым, кроме  
`skills` и `enableSkillCommands`: тюнинг живёт в одном месте.

### Бюджет размышления

`thinkingBudgets` - это **потолок токенов на блок размышления**, и он оказался главной  
причиной, по которой модель ходила по кругу. Свои дефолты pi: `minimal 1024`, `low 2048`,  
`medium 8192`, `high 16384`. В проекте стояло `low: 256` - в восемь раз ниже дефолта pi,  
то есть на самопроверку не оставалось бюджета, и `GlideSystem.ts` переписывался четыре  
раза с одним и тем же конфликтом имён.

Две вещи, которые стоит знать про этот механизм:

- **`xhigh` и `max` не работают.** pi схлопывает оба в `high` (`clampReasoning`), поэтому  
  записи `xhigh: 3072, max: 6144` были мёртвым кодом. В схеме `ThinkingBudgetsSettings`  
  вообще только четыре ключа: `minimal`, `low`, `medium`, `high`.
- **Бюджет обрезается по остатку ответа.** `clampThinkingBudgetToAnswerRoom` держит  
  `thinking ≤ maxTokens - MIN_ANSWER_TOKENS`, где `MIN_ANSWER_TOKENS = 1024`. При  
  `maxTokens: 12288` размышление может занять максимум 11264 токена - то есть  
  размышление и содержимое файла делят один бюджет ответа, и раздувать первое за счёт  
  второго нельзя.

Сейчас стоит `defaultThinkingLevel: "medium"` при `medium: 2048`. Размышление  
расходует и время генерации (на 2060 Super это десятки секунд на ход), поэтому  
`medium` - компромисс: его хватает на самопроверку, но он не съедает ход целиком.

### Разбор логов сессии

Окно pi показывает только ход диалога. Всё, что модель пережила молча - отклонённый  
`write`, `Operation cancelled` от интерактивного вопроса, `npm` не в том каталоге, -  
осталось только в JSONL. Читать его:

```cmd
cmd\pi-log.cmd                       :: список сессий этого проекта
cmd\pi-log.cmd --last                :: сводка по последней
cmd\pi-log.cmd --last --errors       :: только проблемы
cmd\pi-log.cmd --last --tail 3       :: сводка + последнее сообщение модели
cmd\pi-log.cmd --session 01a116ba    :: по id (префикс) или по пути
cmd\pi-log.cmd --all-projects --last :: не фильтровать по каталогу проекта
```

Что печатает:

```
tools   : 25 calls  {'bash': 13, 'write': 11, 'read': 1}

files written (10):            <- реально попавшие на диск
  1x  projects/games/my_game/src/core/Game.ts
  ...

writes that did NOT land (1):  <- вызовы, которые не выполнились
  [14:30:06] projects/games/my_game/src/world/World.ts
      Tool call "write" was not executed: the response hit the output token limit

problems (8):
  [14:20:07] bash: npm failed; path not found
      npm error code ENOENT
```

Важная деталь: «файлы записаны» считается по **результату** вызова, а не по факту  
вызова. `write`, отклонённый из-за лимита ответа, в логе выглядит как обычный вызов -  
но файла на диске нет, и `World.ts` из примера выше именно так и потерялся.

### Чанки без векторов

`index.py` печатает `N with vectors` рядом с общим числом чанков. Расхождение означает,  
что какой-то вход embedding-сервер не принял. Типичная причина - HTTP 500  
`input (N tokens) is too large to process`: один патологически плотный чанк  
(минифицированный бандл) превышает физический батч сервера (`-ub`, он же размер слота  
при `-np`). Embedder обрезает текст до `THREE_EMBED_MAX_CHARS` (6000) и при отказе  
добивает батч поштучно с половинным зажимом, так что штатно этого быть не должно.

Полный текст чанка при этом сохраняется в БД целиком - обрезается только то, что  
уходит в embedding.
