# Three.js RAG Agent Rules

Правила проекта `3GS_Master`. Действуют для **любой** папки внутри репозитория —
в том числе для каждой игры в `projects/games/<name>/`.

## Как читаются эти правила, и почему `AGENTS.md` в папке игры не нужен

**Правило, которое обязано сработать, живёт ТОЛЬКО здесь.** Это не соглашение, а
следствие того, как pi ищет файлы правил (`dist/core/resource-loader.js`):

| Кто | Что видит |
|---|---|
| **pi**, контекст | `AGENTS.md` из `cwd` и из всех папок **ВВЕРХ** до корня диска. В подкаталоги не спускается. |
| **pi**, преамбула | ровно один файл: `<cwd>/.pi/SYSTEM.md`, иначе `<agentDir>/SYSTEM.md` |
| **WorkBuddy** | **только этот файл** в корне проекта |

`agent.cmd` делает `cd /d "%GS_ROOT%"` — то есть `cwd` агента это **корень
репозитория**, а не папка игры. Настоящая цепочка такая:

    <repo>/AGENTS.md                                     <- читается
    F:\Pets\Projects\local_tools\, F:\Pets\, F:\   <- файлов нет

а `projects/games/AGENTS.md` и `projects/games/<игра>/AGENTS.md` — **потомки `cwd`**, и
их не читает никто. Раньше здесь лежала «короткая выжимка для pi»; в промпт она не
попадала ни разу, поэтому её содержимое перенесено сюда, а сам файл удалён.

Полная политика — `ASSET-POLICY.md`, операционная выжимка — скилл
`3gs-local-generation-first`. Не пересказывай их целиком; суть — ниже.

## Где работать: только активный проект, новых не создавать

**Агент работает ВНУТРИ активного проекта.** Папку заводит лаунчер
(`dev.cmd <имя>`, `studio.cmd <имя>`) и записывает её в `data/active_project.txt`.
Внутри может быть **пусто** — это нормальный старт: лаунчер ничего не
раскладывает, файлы создаёт сам агент. Если пользователь не сказал словами
«создай новый проект X» — создавать нечего.

**«То, что уже лежит в проекте, не подходит под задачу» — это НЕ повод создать проект.**
Это повод написать в текущем каталоге ровно то, что просят:

- задача про уровень (платформы, спавны, лимиты камеры) → правится `web3d/level.json`
  (сначала `LEVEL-SCHEMA.md`), потом линтер до кода возврата 0;
- задача про **обычную сцену three.js** — демо, одностраничный HTML, шейдер, эффект →
  **пишется сам файл, и на этом всё.** Ни `level.json`, ни `levels.json`, ни обвязки
  студии, ни скелета;
- задача непонятна → спросить пользователя. Скелет — не ответ на неясную задачу.

Рантайм уже лежит в проекте, копировать его не нужно: `web3d/vendor/`. Страница берёт
его import map'ом и относительным путём:

```html
<script type="importmap">
{ "imports": {
    "three": "./web3d/vendor/three.module.js",
    "three/addons/": "./web3d/vendor/addons/" } }
</script>
```

На CDN не ссылаться (`ASSET-POLICY.md`), и в `levels.json` такую страницу не
регистрировать — это не уровень, и студия на ней сломается.

**Смотреть такую страницу — только через сервер** (`studio.cmd` или `serve.cmd` проекта),
затем открыть `/<файл>.html`. Двойной щелчок по файлу не сработает: браузеры запрещают
ES-модули по `file://`, import map не разрешится, и страница останется пустой.

## Правила Three.js

- Для Three.js API сначала доверяй current official docs и current project code.
- Не смешивай старые и новые версии API без явного указания версии.
- Для addons (`OrbitControls`, `GLTFLoader`, postprocessing и т. п.) проверяй отдельную addon-документацию.
- Для WebGPU/TSL не переносить WebGL-only решения механически.
- Всегда называй точную версию Three.js, когда API version-sensitive.
- Код текущего проекта важнее generic cookbook.
- Не выдавай устаревший CDN/global-script паттерн как современный default.

## Уровень: формат `level.json`

**Перед тем как писать или править уровень, прочитать `LEVEL-SCHEMA.md`.** Это
единственное полное описание формата; там же рабочий пример целиком.

Уровень — обычный JSON (`projects/games/<name>/web3d/level.json`), его читают
`web3d/scene.js` (сцена) и `web3d/engine.js` (игра). Не Godot-сцена, не тайлмап.

Четыре ошибки, из-за которых уровень получается пустым МОЛЧА:

1. `textures` с ключом-**именем** вместо пути. Ключ — путь от корня игры, значение
   — `[ширина, высота]`. Объекта `{url: …}` здесь нет; `scene.js` грузит
   `'../' + ключ`, поэтому имя даёт запрос `/имя` и 404.
2. `frames` заполнен картинками. `frames` — это АНИМАЦИИ:
   `{набор: {анимация: {frames: [пути]}}}`. Одна картинка — `Sprite2D` + `props.texture`.
3. У узла нет `children`. `scene.js` обходит детей без фолбэка → `TypeError`, сцена
   не строится вовсе.
4. Тип написан «по-годотовски»: `Sprite`, `Label`, `TileMap`. Здесь их нет —
   неизвестный тип становится пустой группой и ничего не рисует.

Проверка после записи, код возврата 1 = уровень нерабочий. Шелл агента начинается в
**корне репозитория**, а не в папке игры, поэтому путь к уровню — полный:

```bash
./.venv/Scripts/python.exe tools/level_lint.py projects/games/<name>/web3d/level.json
```

Копия линтера лежит и в каждой игре, так что из её каталога сработает короткая форма
`python tools/level_lint.py web3d/level.json` — но `cwd` по умолчанию не она.

## Ассеты: обязательная политика

**Перед любой генерацией, скачиванием или заменой ассета прочитать
`ASSET-POLICY.md`** (полная версия). Операционная выжимка — скилл
`3gs-local-generation-first` (`.agents/skills/` — для pi, `.workbuddy-ai/skills/` —
для WorkBuddy).

Три правила, которые нарушают чаще всего:

1. **Своя генерация в первую очередь.** Эшелоны, по порядку:

   | Эшелон | Что |
   |---|---|
   | 1. Локальная генерация | персонажи, враги, боссы, оружие, предметы, ключевой арт, заставки, сцены |
   | 2. Локальная генерация + постобработка | апскейл, смена настроения, варианты, кроп |
   | 3. Интернет-ассет | бесшовные тайлы, паттерны, звук, шрифты, референс, заглушка |
   | 4. Спросить | неясно |

   Персонаж, враг или ключевая сцена, которые уже стоят в чужой игре, обесценивают
   проект сильнее, чем сэкономленные полчаса. Поэтому эшелон 1 — не рекомендация.
2. **Облачные генераторы не используются.** `ImageGen`, `VideoGen` и любые
   hosted API — не маршрут. Генерация идёт локальной связкой.
3. **z-image-turbo — движок по умолчанию.** Кто что делает и сколько это стоит:

   | Движок | Когда | Цена |
   |---|---|---|
   | **z-image-turbo** (`bin/sd-vulkan/sd-server.exe` :8687) | по умолчанию: фоны, спрайты, сцены, пропы | ~20 с @768², ~45 с @1856×768, 3.8 ГБ VRAM |
   | ComfyUI `t2i` (Qwen-Image 2.1) | арт с читаемой надписью | ~12 мин, 8.9 ГБ |
   | ComfyUI `color_swap` | точная перекраска с сохранением формы | ~12 мин |
   | ComfyUI `remove_bg_fast` (BiRefNet) | вырезание фона | 24 с |
   | Real-ESRGAN (`bin/Real-ESRGAN-ncnn-vulkan`) | увеличение готовой картинки | 1856×768 → 2× за 14 с; VRAM-арбитраж не занимает |
   | **Pixal3D / TRELLIS.2** (`quality: high`) | **3D по умолчанию**: UV + PBR, реагирует на свет | ~17–18 мин |
   | TripoSplat (`quality: economy`) | 3D-превью; без UV, игнорирует свет | ~3 мин |
   | **Blender** (`BLENDER_EXE`, `blender --background --python`) | **DCC-шаг поверх GLB**: риггинг + анимация, ретопология/UV, конвертация GLB↔FBX, перебейк текстур, превью-рендеры | headless, VRAM-арбитраж не занимает |
   | Qwen2.5-VL-7B (`bin/llama-mtmd`) | посмотреть, что получилось | ~5.5 ГБ VRAM |

   Скорость 3D регулируется **`faces_3d`**, а не `resolution_3d` (замером признан no-op).
   ComfyUI отдаёт сырой GLB и на этом останавливается: всё, что требует *редактирования*
   меша (риг, анимация, ретопо, конвертация), идёт через Blender в headless-режиме.

### Скилл применяется всегда, когда речь об ассете

Признак того, что пора открыть `3gs-local-generation-first`: в задаче есть
**любой** из этих сигналов, независимо от того, просил пользователь «сгенерируй»
или нет — «собери сцену/уровень», «нужен ассет», «сделай арт/фон/заставку/спрайт»,
«продолжи уровень», «сделай glb», «text to image», «text to 3D», «убери фон»,
«увеличь картинку», «доработай игру».

**Формулировка задачи не отменяет политику.** «Собери проект по спецификации» —
это тоже работа с ассетами: если сцене нужен персонаж или ключевой проп, он
делается локальной связкой, а не процедурной заглушкой. Процедурный фолбэк —
это **страховка от блокировки**, а не замена генерации.

## Генерация: один вызов на весь пакет

На машине 8 ГБ VRAM и три модели, которые её хотят целиком (`llama-server`
:8080, `sd-server` :8687, ComfyUI :8188). Поэтому:

- **Сначала полный список ассетов, потом одна генерация.** Не «сгенерируй один
  ассет — посмотрим — ещё один».
- **Источник списка — только двух видов:** (а) сообщение пользователя, (б) сама игра
  (`ls`/`read`: `level.json`, `levels.json`, уже лежащие ассеты). Если субъект не
  назван ни там, ни там — **спросить пользователя**, а не выдумывать. Имена из
  примеров в `SYSTEM.md`/`LEVEL-SCHEMA.md` — это иллюстрации синтаксиса, а НЕ список
  ассетов: брать их как задание = сгенерировать космос для ниндзя.
- **Один запуск на пак:** `./.venv/Scripts/python.exe tools/generate.py
  --project projects/games/<name> --jobs <plan.json>` (или `cmd\gen.cmd`).
- **Несколько вырезаний — одним вызовом:** `asset_remove_bg(images=[...])`, а не по
  вызову на файл. Результат кладётся РЯДОМ с исходником (`<dir>/<stem>-nobg.png`),
  ответ сопоставляет каждый вход с его выходом — переносить ничего не надо.
  **Затыкать дыру копированием одного ассета под чужим именем нельзя:** сцена с
  подменённой картинкой рисуется без единой ошибки — это худший из возможных провалов.
  Вырезание упало — прочитать путь из ошибки и позвать снова.
  Пути можно давать от корня проекта (как в паке) или абсолютные; `name` — обычный
  слаг, суффикс `-nobg` дописывается сам.
- **Кто держит карту:** `generate.py --status`. Пока идёт пак, `llm :8080 : down`
  — норма, а не падение. Не поднимать движок руками рядом с LLM.
- **VRAM — строго по одному:**

  ```
  не более одного из:  llama-server :8080  XOR  sd-server :8687  XOR  ComfyUI :8188
  ```

  Real-ESRGAN и Blender — исключения, они не считаются (оба держат сотни МБ и
  работают рядом с любым движком).
- **`faces_3d` для 2D:** дефолт графа 700 000 ≈ 40 МБ на проп, спрайту хватает
  5 000–20 000. `steps_3d` — суммарно 56 шагов на 4 сэмплера, время почти линейно.

## Запуск агента

Только лаунчеры (`dev.cmd`, `agent.cmd`, `studio.cmd`, `serve-all.cmd`, `resume.cmd` — в
корне;
`cmd\ask.cmd`, `cmd\index.cmd`, `cmd\doctor.cmd`, `cmd\gen.cmd`, `cmd\check.cmd`, … — в
`cmd\`) либо единый фасад `gs.cmd`. `pi` напрямую нельзя — подхватится глобальный
`~/.pi/agent` с чужими MCP и провайдером.

**Основной способ работы — консольный агент, а не студия.** Вся цепочка — одним
лаунчером:

```cmd
cd /d F:\Pets\Projects\local_tools\3GS_Master && dev.cmd <имя игры> [--studio]
```

`dev.cmd` = `serve-all.cmd` (модели) → `cmd\doctor.cmd` (проверка) → необязательная
студия в **отдельном окне** → `agent.cmd projects\games\<имя>`. Аргумент — **имя игры**, не путь.
Без `--studio` получается чистая CLI-сессия; со `--studio` параллельно открывается
студия для живого просмотра.

**`dev.cmd` ничего не создаёт, кроме самой папки.** Заводит пустой
`projects\games\<имя>\` и сразу передаёт его агенту: ни `scene.js`, ни `level.json`,
ни `tools\`, ни `serve.py` там не появятся — файлы пишет сама модель, пустая папка
это нормальный старт. Стандартный стек кладёт **только явный** `newgame.cmd <имя>`
(`--sync` — обновить стек, `--force` — перезаписать и уровни, `--cli` — слой без
студии). Флаги `--force` и `--cli` у `dev.cmd` убраны и отбиваются сообщением
`no longer a dev.cmd flag` (rc=2): они делали ровно то автосоздание, от которого
избавились. У `dev.cmd` остались `--studio` / `--no-studio`.

**Источник стека — репозиторий, а не соседний проект.** Что попадает в новый
проект и откуда, сказано ОДНОЙ таблицей `STACK_SRC` в `tools/new_game.py`:
`web3d/vendor/` ← `vendor/three/` (three.js r186), `web3d/scene.js` ←
`stack/web3d/scene.js`, остальное ← `tools/`. Раньше стек копировался из первой
попавшейся игры (`find_sample`), и удаление одной игры останавливало создание
всех остальных; флага `--from` больше нет. Общий файл правится В ИСТОЧНИКЕ
(`stack/`, `vendor/three/`, `tools/`), а не внутри одного проекта: правка в
проекте чинит ровно один проект и молча разводит остальные. Разложить стек
заново в существующем проекте — `--sync`.

**Ревизия рантайма зафиксирована.** `vendor/three/` — r186, та же, на которую
написана документация в `knowledge/`. Поднять её — значит получить документацию,
которая врёт про API. Сборка r186 разбита: рядом с `three.module.js` обязан
лежать `three.core.js`.

То же вручную, если нужно по шагам:

```cmd
cd /d F:\Pets\Projects\local_tools\3GS_Master && serve-all.cmd && cmd\doctor.cmd && agent.cmd projects\games\<имя>
```

> **Эта строка — для окна `cmd.exe` ПОЛЬЗОВАТЕЛЯ, а не для агента.** У агента шелл —
> bash (Git Bash), и `.cmd` из него не запускаются вовсе: `serve-all.cmd` даёт
> `command not found` (exit 127). Агенту не нужно поднимать модели и не нужно
> запускать `agent.cmd` — их уже запустил пользователь. Из bash агент зовёт
> python-скрипты напрямую:
> `./.venv/Scripts/python.exe tools/tscheck.py projects/games/<game>`,
> `./.venv/Scripts/python.exe tools/level_lint.py projects/games/<game>/web3d/level.json`.

То же самое одной подкомандой: `gs dev <игра> [--studio]`, либо по шагам
`gs up` (модели) → `gs agent <игра>`. Полный список подкоманд — `gs help`.

`serve-all.cmd` поднимает обе модели в отдельных окнах и **блокирует**, пока они
не ответят, поэтому `&&` безопасен.

**`:8080` — роутер, а не одна модель.** `cmd\serve-llm.cmd` читает реестр
`models\llm-preset.ini`, который генерирует `tools\llm_models.py` из `models\` и
`GS_LLM_MODELS_DIR` (по умолчанию `E:\Programs\LocalLLM\Models`), и отдаёт в
`/v1/models` все найденные GGUF. Модель грузится по первому запросу, при
`--models-max 1` предыдущая выгружается — на 8 ГБ это единственный безопасный режим.
В pi переключение это `/model`; профиль, RAG, скиллы и MCP при этом не меняются.
Список и пересканирование — `cmd\models.cmd [--refresh]`, подробности —
`docs\LLM-MODELS.md`.

**Студия — отдельный инструмент, и агента в ней нет.** Модель работает только
через консольный `pi`, а студия (`studio.cmd`) — живой просмотр и ручная правка:
уровень 2D/3D, превью картинок и просмотрщик GLB. Она **необязательна** и
запускается **параллельно, в любой момент, независимо** от агента — отдельным
окном:

```cmd
cd /d F:\Pets\Projects\local_tools\3GS_Master && studio.cmd <игра>
```

Смысл связки: агент правит `level*.json` в консоли, а студия показывает
результат — открой или перезагрузи страницу, и видно, что он изменил; там же
это можно поправить мышью. Ни чата, ни ручки `/__ask` у сервера студии нет:
браузер не порождает процессы, а запускать агента, умеющего писать файлы, из
сервера незачем. Подробности в `README.md` («Быстрый старт») и `STUDIO.md`.

Если `serve-all.cmd` не открыл окна — это не поломка: оба порта уже заняты
(осиротевший `llama-server` пережил закрытие консоли). Кто держит:
`.venv\Scripts\python.exe tools\wait_ready.py --status`; перезапуск:
`serve-all.cmd --restart`.

## Прочее

- **Не удалять файлы, которые не просили удалять.**
- Сгенерированное — сырьё: кроп под пропорции уровня + равномерный скейл.
- Интернет-ассет: лицензия прежде файла, запись в `CREDITS`, сообщить
  пользователю, что скачано.
- Проверка игры — гейт, а не вежливость: `cmd\check.cmd <game>` для типов
  (из bash: `./.venv/Scripts/python.exe tools/tscheck.py projects/games/<game>`),
  `python tools/level_lint.py web3d/level.json` из каталога игры для уровня
  (код возврата 1 при падении).
- **Страница проверяется до того, как её откроет пользователь:**
  `cmd\check.cmd <game>` после tsc гоняет второй гейт —
  `./.venv/Scripts/python.exe tools/pagecheck.py projects/games/<game>`.
  Он резолвит каждый модульный спецификатор через importmap самой страницы и
  проверяет, что файл есть, потом то же для ассетов. Зачем: импорт, который 404-ит,
  не «портит» страницу, а **обрывает граф модулей целиком** — `init()` не
  выполняется, в студии пустой холст и ни одной ошибки вне devtools. Ровно так
  уехал готовый на вид `ninja.html` с
  `import { TextureLoader } from 'three/addons/loaders/TextureLoader.js'`:
  в `vendor/three/addons/loaders/` лежит только `GLTFLoader.js`, а `TextureLoader`
  живёт в ядре и реэкспортируется из `three`. Отсутствующий ассет ещё тише:
